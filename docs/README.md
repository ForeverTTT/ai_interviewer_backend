## 维护规则

1. **每篇文档开头写元信息**：状态（现行 / 待补充 / 脚手架 / 已实施 / 已废弃）、最后核对日期，有对应代码时写出代码路径。
2. **一个事实只写一处**：接口写在 API 参考，表写在数据库参考，环境变量写在环境变量文档，其他文档只链接，不复制。
3. **产品和技术分开写**：规则（阈值、次数、扣费）由产品文档定义，技术文档说明怎么实现。判断方法：换一套技术栈重写，这段话还成立吗？成立的放 01，不成立的放 03 / 04。
4. **产品和技术文档一一对应**：`01-产品/功能说明/` 和 `03-技术与架构/` 按侧栏入口同名对应，两篇开头互相链接。新增一个侧栏入口时，两边各加一篇；跨模块的内容分别放进 `01-产品/通用规则.md` 和 `03-技术与架构/通用机制/`。
5. **改代码时同步改文档**：新增路由 → API 参考；新增 migration → 数据库参考；新增环境变量 → 环境变量文档和 `.env.example`；行为变化 → 对应的领域文档。
6. **方案的生命周期**：新方案放在 `06/进行中/`；落地后把结论更新到 01 和 03，再把方案移到 `06/已实施/`，并在开头注明落地时间和现行文档链接，之后不再维护。
7. **文档中的已知问题**：在领域文档的"已知问题 / 已知限制"一节记录，并在[问题与想法](问题与想法.md)中登记，修复后两处一起删除。
