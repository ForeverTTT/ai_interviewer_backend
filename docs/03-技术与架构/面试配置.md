# 面试配置

> 状态：现行 · 最后核对：2026-10-01 · 产品说明：[面试配置](../01-产品/功能说明/面试配置.md)
> 代码：`frontend/src/pages/SetupPage.jsx`、`frontend/src/lib/jobDescriptionParser.js`、`backend/src/routes/interviews.js`（`POST /`）、RPC `create_interview_session`

用户在 `/setup` 填写配置，后端原子地创建面试并扣费，然后前端跳转到 `/interview/:interviewId`。之后面试如何进行见[模拟面试 · 面试流程](模拟面试/面试流程.md)。

## 1. 前端流程

```text
填写表单 → 本地校验（职位必填、JD ≥ 50 字）→ 余额预检查（< 300 直接提示，不发请求）
  → POST /api/interviews（同一个 idempotencyKey，网络失败时 500 ms 后重试一次）
  → navigate('/interview/:id', { state: 首屏配置 })
```

| 机制 | 实现 |
|---|---|
| 幂等键 | 一次"开始"动作生成一个 `idempotencyKey`，存在 ref 中，失败重试时复用，创建成功后清空 |
| 简历选择 | 先读 `GET /api/profile/resume`；本场上传的 PDF 解析后同时 `PUT /api/profile` 保存；截取前 50,000 字符作为 `resume_snapshot` |
| 时长 | 滑条 5–60 分钟、步长 5。练习模式不显示滑条，按难度显示题量（见[面试流程 · 题量](模拟面试/面试流程.md#95-题量)） |
| 预填 | 从 Offer 冲刺任务进入时，读取 `location.state.offerSprintDefaults` 预填岗位、JD、面试类型、模式和时长 |
| JD 历史 | `localStorage` 的 `interviewde_jd_history`，最多 10 条 |
| 错误映射 | 401 / `AUTH_EXPIRED` → 登录失效提示；403 / `INSUFFICIENT_TOKENS` → 能量值不足；其他 → 通用创建失败 |

## 2. JD 解析

`lib/jobDescriptionParser.js` 在**浏览器本地**用加权正则识别雇佣类型、行业类别和职位名称，支持英、德、中三种语言的关键词，不调用后端，也不扣费。`SetupPage` 和 `ResumeTailorPage` 共用。

后端的 `POST /api/ai-assistant/analyze-job-description` 是功能相似的规则实现（同样不调用 AI），**当前前端没有调用**。

## 3. 创建接口


### 3.1 创建输入

`POST /api/interviews` 接收并持久化以下核心配置：

- `position`：应聘职位；
- `job_description`：完整职位描述快照；
- `language`：面试语言；
- `duration`：正式模式 5–60 分钟；练习模式仍携带兼容值，但不建立 deadline；
- `resume_snapshot`：用户资料中的简历或本次临时简历快照；
- `role_track`：求职方向，例如工作/学校路径；
- `mode`：`practice` 或 `formal`；
- `difficulty`：`easy`、`medium`、`hard` 或 `adaptive`；
- `interviewer_style`：面试官表达风格；
- `interviewer_type`：`hr`、`technical` 或 `mixed`；
- `competency_matrix`：由 JD 和简历生成的能力矩阵；
- `idempotencyKey`：创建请求幂等键。

前端当前还会提交 `employment_type`（实习、全职、学生工、兼职、合同），但后端创建路由和
`create_interview_session` RPC 尚未接收或持久化该字段，也不会据此改变题目路线。当前真正进入后端
面试配置的仍是旧字段 `role_track=school/work`。这两者不能在文档或代码中视为同一个字段。

### 3.2 原子创建

创建通过 Supabase RPC `create_interview_session` 完成，而不是由多个 HTTP 写操作拼接：

```text
锁定 profiles 用户行
  → 检查 interview_creation_requests 是否已有同幂等键结果
  → 检查积分余额
  → 一次性扣除面试积分
  → 插入 interviews 与初始配置
  → 保存幂等响应
  → 返回 interviewId、deadline 和 replay 标记
```

当前默认面试成本由后端传入 `300` tokens。同一用户的并发创建会在 profile 行锁上串行，避免使用
不同幂等键绕过余额检查。

### 3.3 快照语义

`job_description_snapshot` 和 `resume_snapshot` 在创建时固定。后续用户修改个人资料简历、JD 历史或
职位信息，不改变已创建面试的 Agent 上下文和报告证据。


`create_interview_session` 只允许 Service Role 调用（`20261001120000_billing_authorization_hardening.sql`），因此后端用 `lib/supabase.js` 的 `supabase` 客户端调用，扣费金额由后端固定传入，见[账户与计费 · 谁可以改余额](通用机制/账户与计费.md#3-谁可以改余额)。
