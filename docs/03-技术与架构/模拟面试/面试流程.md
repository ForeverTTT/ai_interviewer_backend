## 2. 系统边界与核心原则

后端由 Node.js/Express 运行在 Cloud Run，Supabase PostgreSQL 保存业务事实，Gemini 提供文本推理、
报告和 Live 音频能力。

```text
Web / Mobile Browser
   │
   ├─ REST JSON ────────────────┐
   ├─ SSE（兼容文本面试）───────┤
   └─ WebSocket（Gemini Live）──┤
                                ▼
                     Express + WebSocket Server
                         │       │       │
                         │       │       └─ Gemini API / Gemini Live
                         │       └─ LangGraph / interviewLearning
                         ▼
                   Supabase PostgreSQL
       interviews / questions / attempts / messages / events / requests
```

核心原则：

1. `interviewId` 是所有读取、写入、恢复和实时连接的业务边界。
2. PostgreSQL 是业务状态事实来源；Cloud Run 进程内存和 WebSocket 只保存临时连接状态。
3. 创建、回答、下一题、提示和状态动作必须幂等，网络重试不能重复扣分或重复写入。
4. `state_version` 通过乐观锁阻止并发请求覆盖较新的面试状态。
5. 面试配置使用创建时快照，个人资料后续变化不能污染历史面试。
6. 正式面试的 `deadline_at` 由服务器强制执行；浏览器倒计时不是权威时间。
7. 练习和正式模式可以共享 UI 与 Live 传输层，但不能共享推进权限。

## 5. 面试聚合状态

### 5.1 Interview 状态

`interviews.status` 允许：

```text
draft → active ↔ paused → finalizing → completed
                     └──────────────→ abandoned
```

- `draft`：记录已创建但尚未产生有效面试回合；
- `active`：可以接收当前模式允许的动作；
- `paused`：仅练习模式使用；
- `finalizing`：面试内容锁定，等待或正在生成报告；
- `completed`：报告已保存；
- `abandoned`：业务终止，不再接受面试动作。

状态与报告状态分开保存。`finalize_status` 允许：

```text
not_started → processing → completed
                       └→ failed → processing（重试）
```

### 5.2 Question 状态

`interview_questions.status` 允许：

```text
pending / active / answered / mastered / skipped
```

正式模式回答后即完成当前问题；练习模式回答后可以继续请求反馈、重答，最终由 `master` 或 `skip`
解决当前题并取得下一题资格。

### 5.3 Checkpoint 与关系型事实

`graph_state_json` 保存轻量可恢复 checkpoint，例如 `phase`、`plan`、`planIndex`、计数器和固定配置。
它不是完整消息历史。

问题、回答、提示、笔记和证据使用规范化表保存；`transcript_json` 作为旧客户端和报告输入的兼容读模型。

## 6. 两种执行通道

当前系统不是“所有语音回合都直接执行一次 LangGraph”。后端存在三条有明确用途的通道：

| 通道 | 主要用途 | 推进方式 |
|---|---|---|
| Gemini Live WebSocket | 正式语音面试；练习语音朗读与转写 | 正式由 Live 对话推进；练习由应用动作推进 |
| REST 练习状态机 | 练习题、回答、反馈、提示和状态动作 | PostgreSQL RPC 原子推进 |
| SSE 文本链路 | 文本面试和兼容路径。**当前前端未启用**（所有面试都走 Live） | LangGraph 每轮路由并提交 checkpoint |

三条通道共享 `interviewId`、持久化配置、checkpoint、消息和题目/回答事实，但生成引擎不同：

- LangGraph 节点与 Prompt 细节见[agent与Prompt](agent与Prompt.md)；
- 正式 Live 的每个语音 turn 由 Gemini Live 会话生成，并由 WebSocket 层写入问题与回合；
- 练习下一题由 `interviewLearning.generateInterviewQuestion` 根据固定计划阶段生成，不允许 Live 自主推进。

## 7. 正式模拟流程

### 7.1 完整流程

```text
创建 formal interview
  → RPC 设置 started_at、active_since、deadline_at
  → WebSocket start 携带 JWT + interviewId
  → 后端验证用户、Origin、面试归属和状态
  → 从 PostgreSQL 恢复 checkpoint 与有限 transcript
  → 连接 Gemini Live 并注入创建时配置
  → Live 提问、候选人回答、回合完成
  → 问题/回答/消息/checkpoint 原子持久化
  → 路线完成、用户结束或 deadline 到达
  → status=finalizing
  → finalize 抢占并生成报告
  → status=completed + report_json
```

### 7.2 正式模式约束

- 不允许暂停、提示、笔记或重答；
- 中途不向客户端返回评分或反馈；
- 服务端 `deadline_at` 不会因为刷新或重连而重置。**但当前前端在离开或关闭页面（`pagehide`）时会触发 finalize，所以离开页面就会结束正式模拟**，见[问题与想法](../../问题与想法.md)；
- 重连时只恢复当前面试的有限历史；
- deadline 后不得创建下一题；
- 报告从已持久化 transcript 和规范化 attempts 读取证据。

### 7.3 题量与路线接口

正式时长由用户在 5–60 分钟内选择。核心题槽计算：

```text
maxQuestions = clamp(floor(duration / 2.5) + 1, 3, 20)
```

开场自我介绍独立于核心题槽。业务层只保存有序路线和当前进度；经历深挖、技术、行为阶段如何分配、
Agent 如何选择节点和 Prompt，统一由[agent与Prompt](agent与Prompt.md)说明。

## 8. 正式计时与最后一题宽限

### 8.1 权威时间

创建 formal interview 时，数据库设置：

```text
deadline_at = now() + duration
```

读取 workspace、建立 Live 连接和相关动作都会调用 `expire_formal_interview_if_due`。浏览器倒计时负责
显示和及时触发结束，但不能延长服务器 deadline。

### 8.2 截止状态转换

```text
deadline reached + current_question_id is null
  → status=finalizing
  → checkpoint.phase=closed
  → closeReason=formal_deadline_reached

deadline reached + current_question_id exists
  → 保持当前问题可回答
  → 不允许创建新问题
  → complete_formal_answer_after_deadline 原子保存唯一答案
  → current_question_id=null
  → status=finalizing
  → closeReason=formal_deadline_answer_completed
```

宽限只适用于 deadline 前已经展示的问题，不允许重答，也不是额外固定分钟数。候选人提交当前答案后
立即结束，不继续追问。

## 9. 练习模式流程

### 9.1 完整流程

```text
创建 practice interview（deadline_at=null）
  → 加载 workspace
  → 没有当前题时显式 POST /questions/next
  → 问题落库后发送 PRACTICE_CONTROL 让 Live 朗读一次
  → 候选人语音转写到可编辑答案
  → 用户显式提交答案
  → 后端保存 attempt、反馈、能力证据和 Adaptive 难度
  → 用户可 hint / note / retry
  → 用户显式 master 或 skip
  → 用户点击下一题后再次 POST /questions/next
  → 达到题量后 finalize
```

### 9.2 Live 输出闸门

练习模式下，Gemini Live 不是问题路线控制器：

- 麦克风音频用于实时输入转写；
- 候选人停顿导致 Live turn complete 时，服务端默认屏蔽模型文本和音频；
- Live turn complete 不创建 attempt，也不创建下一题；
- 只有带 `[PRACTICE_CONTROL]` 的显式题目朗读消息临时打开一次模型输出；
- 提交、反馈、重答、掌握、跳过和下一题均由 REST + PostgreSQL 状态机控制。

这避免了候选人尚未回答完时 AI 插话，或停顿后自动进入下一题。

### 9.3 手动推进规则

- `answer` 只保存并分析当前答案，不生成下一题；
- 再次回答前必须先成功执行 `retry`；
- 新 attempt 不覆盖历史 attempt；
- `master` 要求当前题已经有回答；
- `skip` 可以保存最多 200 字的原因事件；
- 当前题未 `mastered/skipped` 时，`questions/next` 返回 409；
- 下一题规划读取最近三道题的最新回答、分数、缺口和 next steps；
- 模型生成设置 15 秒上限，失败或超时时按当前阶段生成本地备用题。

### 9.4 提示与反馈

提示层级固定为：

```text
nudge → structure → key_points → example
```

练习回答会保存结构化反馈和能力证据。正式模式即使为了 Adaptive 难度进行内部分析，也会在 HTTP
响应中清除 `feedback_json`，避免面试中泄露评价。

### 9.5 题量

练习不限时，滑条不参与结束判断；题量由难度决定，并覆盖完整面试路线：

| 难度 | 等价正式时长 | 核心题槽 | 含开场总题数 |
|---|---:|---:|---:|
| Easy | 10 分钟 | 5 | 6 |
| Medium | 20 分钟 | 9 | 10 |
| Adaptive | 20 分钟 | 9 | 10 |
| Hard | 45 分钟 | 18 | 19 |

后端 `practiceLimitState` 返回题量限制和 elapsed 观测值，但 `durationSeconds/remainingSeconds` 为 null，
不会因时间自动结束。达到题量后后端禁止继续生成题目，客户端触发 finalize。

## 10. 难度、面试官类型与岗位证据

### 10.1 难度

- Easy：基础、明确、低压力；
- Medium：岗位核心场景、应用判断和具体证据；
- Hard：模糊约束、权衡、失败模式和验证；
- Adaptive：初始按 Medium 执行，回答评分 `>=85` 升一级、`<=55` 降一级，其余保持。

### 10.2 面试官类型与风格

`interviewer_type` 决定题型允许范围、路线 pattern、RAG 偏好和报告关注点；`interviewer_style` 决定
表达语气和 Live voice。类型与风格在创建时持久化，恢复、文本、Live 和报告读取同一份配置。

具体策略见[面试官类型选择方案](../../06-决策与方案/已实施/面试官类型选择方案.md)。

### 10.3 能力矩阵与 RAG

后端根据 JD 与简历关键词生成初始能力矩阵；问题可以关联 competency、rubric、source 和
source_metadata。练习回答会写入 `interview_competency_evidence`，支持跨场练习进步汇总。

面经检索只返回与 position、JD 和面试官类型相关的有限文档；检索算法和 Agent 使用方式见
[agent与Prompt](agent与Prompt.md)。

## 11. 数据模型

| 表 | 用途 |
|---|---|
| `interviews` | 聚合根、配置快照、状态、deadline、checkpoint、当前题、报告和 finalize 状态 |
| `interview_creation_requests` | 创建幂等响应，防止重复扣分和重复创建 |
| `interview_requests` | 面试动作/回合幂等 claim、pending、replay 和失败释放 |
| `interview_messages` | 按 sequence 保存可恢复的 user/assistant/system 消息 |
| `interview_questions` | 问题文本、顺序、类型、能力、难度、来源、rubric 和状态 |
| `interview_attempts` | 每道题的多次回答、反馈、提示使用层级和 attempt_number |
| `interview_hints` | 练习模式四级提示 |
| `interview_notes` | 用户私人练习笔记 |
| `interview_competency_evidence` | 回答评分、原文证据和 rubric |
| `practice_progress_reports` | 跨多场练习的进步报告快照 |
| `interview_events` | append-only 生命周期与错误事件，不保存 Prompt、token 或原始音频 |

所有业务表以 `interview_id` 关联；用户读取受 RLS 限制，后端写入同时在应用层校验 `user_id`。

## 12. 一致性、幂等与并发

### 12.1 请求幂等

写操作从 body `idempotencyKey`、`Idempotency-Key` 或请求 ID 取得稳定键：

```text
claim_interview_request
  → 已完成：返回保存的 response + replay=true
  → 正在处理：返回 pending/409
  → 新请求：写入 pending claim
```

模型或数据库操作失败时，后端释放 pending claim，使同一个业务动作能够安全重试。

### 12.2 乐观锁

每次动作携带读取时的 `expectedVersion`。RPC 在事务中比较 `state_version`：

- 相同：执行动作并把版本加一；
- 不同：返回 409 和 `currentVersion`，客户端应重新加载 workspace；
- 禁止用旧客户端状态覆盖另一标签页或另一实例刚写入的结果。

### 12.3 事务边界

以下操作必须由数据库 RPC 原子完成：

- 创建面试与扣积分；
- 提交 checkpoint、消息和 transcript；
- 问题/回答/提示/状态动作；
- 正式 deadline 到期；
- deadline 后最后答案保存；
- finalize 锁抢占。

## 13. 实时语音与断线恢复

### 13.1 WebSocket 建连

路径：`/api/chat/live`。

浏览器第一条 JSON 消息必须是：

```json
{
  "type": "start",
  "token": "<Supabase access token>",
  "config": { "interviewId": "<uuid>" }
}
```

后端在 10 秒内验证 token，检查 Origin、面试归属、状态和 deadline，然后只从数据库读取该
`interviewId` 的 checkpoint、当前题与有限 transcript。客户端传入的职位/JD 等配置不能覆盖持久化配置。

### 13.2 音频协议

- 浏览器上传 PCM 16 kHz 二进制音频；
- Gemini Live 输出 PCM 24 kHz base64 音频；
- `input_transcript` 和 `output_transcript` 以 JSON 增量发送；
- `turn_complete` 标记一个 Live turn 的转写完成；
- `interrupt`、`audio_end` 支持中断与结束输入流；
- 练习模式按第 9.2 节执行输出闸门。

### 13.3 恢复语义

WebSocket 对象和 Gemini Live session 不持久化。断线后：

1. 客户端重新建立 WebSocket；
2. 后端重新验证 JWT 与面试归属；
3. 从 Supabase 恢复 checkpoint、当前问题和最近有限消息；
4. 新建 Gemini Live session 并注入恢复上下文；
5. 继续使用同一个 `interviewId` 和新的幂等请求键提交后续回合。

意外关闭会清理连接、收音和播放状态，客户端按 1、2、4 秒最多自动重试三次。用户主动结束或服务端 1008 拒绝不自动重连。Live 对话仅由后端保存，前端不再并行自动保存 transcript；版本冲突会重新读取并有限重试。诊断事件、关闭码和恢复边界见[实时语音与 TTS · 连接恢复与诊断日志](实时语音与TTS.md#111-连接恢复与诊断日志)。

`GET /api/interview-sessions/:id/reconnect-context` 只返回必要上下文，避免把整份历史或其他面试带入模型。

## 16. 认证、安全与隔离

- REST 请求通过 `requireAuth` 验证 Supabase JWT；
- WebSocket `start` 消息单独验证 token，并有 10 秒鉴权超时；
- 生产与本地 Origin 使用允许列表；
- 查询同时包含 `interview_id` 与当前 `user_id`；
- 数据库启用 RLS，用户只能读取自己的面试数据；
- 正式完成前事件接口隐藏中间评分；
- `interview_events` 不保存 Prompt、access token、原始音频或完整 Secret；
- Express 使用 Helmet、CORS、请求体限制和 API rate limiting；
- Service Role 只存在后端环境变量，不能下发前端。

## 17. 可观测性

每个 HTTP 请求有 request ID。面试关键路径写入 append-only `interview_events`，包括：

- finalize 点击、请求、响应、开始、完成和失败；
- 页面退出；
- deadline 到达及是否使用答题宽限；
- 重连；
- 跳过原因；
- 模型、stage、HTTP 状态、耗时、attempt 和有限错误摘要。

`interviews` 同时保存 `finalize_attempts`、`finalize_last_error_stage`、`finalize_model`、
`finalize_started_at` 和 `finalized_at`，用于区分网络问题、模型失败、JSON 解析失败和数据库保存失败。

## 18. 失败与降级

| 故障 | 当前处理 |
|---|---|
| 练习问题模型超时/失败 | 15 秒后使用当前阶段的本地备用题，并释放 pending claim |
| 重复提交 | 幂等响应 replay，不重复写入 |
| 并发版本冲突 | 返回 409 + currentVersion，客户端重新加载 |
| Live 断线 | 从 Supabase 恢复，建立新 Gemini session |
| Live 持久化失败 | 释放相关 request claim，发送通用错误，允许重连重试 |
| deadline 到达 | 无当前题直接 finalizing；有当前题只允许完成一次 |
| finalize 并发 | 只有一个请求取得锁，其余返回 202 |
| finalize 模型/解析/保存失败 | 记录失败 stage 和 retryable 状态，允许后续重试 |
| TTS 失败 | TTS 专项链路按[实时语音与 TTS](实时语音与TTS.md)的降级策略处理 |

错误响应不得把 Google/Supabase 凭证、内部 URL 参数或完整第三方错误对象暴露给客户端。

## 19. 数据库迁移顺序

面试主链路依赖的 migration 从 `20260822223000_interview_observability.sql` 到 `20260824153000_formal_answer_completion_grace.sql`，必须按时间顺序全部执行。完整清单见[数据库参考 · Migration 清单](../../04-参考/数据库.md#migration-清单)，发布流程见[数据库迁移发布](../../05-运维/数据库迁移发布.md)。

Cloud Run 自动部署不会自动执行 Supabase migration。应用发布前要确认生产 schema 已包含代码调用的 RPC 签名，否则 PostgREST 会返回 `PGRST202`。

## 20. 测试与验收

后端 `npm test` 当前覆盖：

- Session checkpoint、消息清洗和隔离；
- 幂等请求 claim/release；
- 乐观锁与冲突包装；
- 难度、题量、能力矩阵、RAG 排序和练习反馈；
- 正式截止和最后答案宽限辅助函数；
- 面试官类型与风格策略。

`backend/test/sql/interview_sessions_integration.sql` 验证数据库事务、同用户多面试隔离、动作规则和并发冲突。

上线验收还必须包含真实浏览器/设备测试：

- 麦克风权限、16 kHz 上传与 24 kHz 播放；
- 候选人停顿时练习模式不出声、不自动下一题；
- 多段转写可以编辑后再提交；
- 刷新和断线恢复到同一题；
- 正式 deadline 到达时可以答完当前题且绝不产生新题；
- finalize 失败可恢复，报告不会重复生成；
- 中文、英语、德语的题目、语音与报告语言一致。

## 21. 当前限制与后续演进

1. `employment_type` 目前只存在于前端提交数据，后端尚未持久化，也未用于 Agent 路线；需要增加字段、
   RPC 参数、迁移和恢复映射后才能成为可靠的面试配置。
2. 报告生成还不是独立持久任务队列；真正“结束后立即离开页面”需要后台 job/worker。
3. Gemini Live 会话只能存在于单个 Cloud Run 实例，恢复依赖重新建连而不是连接迁移。
4. `transcript_json` 仍作为兼容读模型存在，新功能应优先读取规范化 questions/attempts/messages。
5. 练习问题已有本地 fallback，但反馈和最终报告仍依赖模型服务。
6. 真实语音质量、浏览器权限和网络抖动不能只靠单元测试，需要持续端到端回归。
7. 当前 Cloud Run 最多 2 个实例；扩容时仍应保持数据库为唯一事实来源，不能重新引入进程内全局 Session。
