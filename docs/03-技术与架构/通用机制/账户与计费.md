# 账户与计费

> 状态：现行（未接入支付） · 最后核对：2026-10-01 · 产品说明：[通用规则 · 账户与登录、能量值](../../01-产品/通用规则.md)
> 代码：`backend/src/middleware/auth.js`、`backend/src/middleware/tokens.js`、`backend/src/routes/profile.js`、`frontend/src/lib/authenticatedFetch.js`、`frontend/src/hooks/useAccountStatus.js`

登录流程见[首页与登录](../首页与登录.md)；本文说明所有模块共用的请求鉴权和能量值。

## 1. 后端鉴权

| 机制 | 说明 |
|---|---|
| `requireAuth` | 读取 `Authorization: Bearer <access_token>`，用 Service Role 客户端调用 `auth.getUser(token)` 验证。成功后设置 `req.user` 和 `req.accessToken`；失败返回 401，错误码 `AUTH_TOKEN_INVALID` |
| 面经接口 | `routes/experiences.js` 没有使用 `requireAuth`，而是在各个处理函数里自己验证 token（`GET /` 完全公开） |
| WebSocket | `start` 消息里单独携带 token 验证，10 秒内未通过鉴权就断开 |
| 前端 401 处理 | `authenticatedFetch` 刷新一次 token 后重试；如果仍然是 401，再向 Supabase 确认会话是否有效。只有 Supabase 也判定失效时才清除登录状态，否则抛出 `BACKEND_AUTH_REJECTED`，避免后端配置问题把用户踢下线 |

## 2. 能量值（Tokens）

界面上叫"能量值"，代码和数据库中叫 `tokens`，存放在 `profiles.tokens`（整数，`>= 0`，默认 1000）。

### 2.1 消耗

| 操作 | 接口 | 消耗 | 扣费方式 |
|---|---|---:|---|
| 创建面试（练习或正式） | `POST /api/interviews` | 300 | RPC `create_interview_session` 在同一事务中创建面试并扣费，相同幂等键不会重复扣 |
| 从收藏题开始针对性练习 | `POST /api/growth-center/collections/:id/practice` | 300 | 同上 |
| 简历结构化提取 | `POST /api/profile/extract-cv` | 50 | 先检查余额，AI 成功后再扣 |
| 简历诊断（简历教练） | `POST /api/profile/resume-coach` | 200 | 先检查，结果保存成功后再扣 |
| 按 JD 改写简历 | `POST /api/ai-assistant/tailor-resume` | 100 | 先检查，成功后再扣 |
| 生成动机信 | `POST /api/ai-assistant/generate-motivation-letter` | 100 | 先检查，成功后再扣 |
| 盖洛普结果分析 | `POST /api/gallup/analyze` | 100 | 先检查，保存成功后再扣 |
| 删除自己分享的面经 | `DELETE /api/experiences/:id` | 200 | 收回分享时获得的奖励 |

余额不足时返回 `403`，错误码 `INSUFFICIENT_TOKENS`。前端在报告页等位置会引导用户前往 `/profile`。

除创建面试外，其他扣费分为两步：`checkTokens` 中间件先检查余额，`deductTokens` 在成功后调用 RPC `deduct_user_tokens` 扣除（余额最低扣到 0）。**这两步之间没有加锁**，并发请求可能都通过检查。由于扣费下限是 0，余额不会变成负数，但可能出现少扣。

文本面试过程中的消息、TTS、Live 语音、报告生成和翻译**不额外扣费**，费用已经包含在创建面试的 300 里。

### 2.2 获得

| 方式 | 接口 | 数量 | 规则 |
|---|---|---:|---|
| 注册 | 数据库默认值 | 1000 | 一次性 |
| 每日打卡 | `POST /api/profile/check-in` | 200 | 每个自然日一次。连续打卡天数存放在 `daily_streak` 中，中断一天以上就重置为 1。**当前前端没有调用这个接口**（`CheckInModal` 组件也没有被任何页面引用） |
| 分享面经 | `POST /api/experiences` | 200 | 每个用户每个 UTC 自然日最多分享 1 篇（超过返回 429 `DAILY_LIMIT`） |

目前没有充值渠道。界面上的"获取能量"按钮打开的是引导弹窗（分享面经、关注小红书），不会直接加余额。原来的模拟充值接口 `POST /api/profile/recharge` 已经在 2026-10-01 删除。

`addTokens` 的实现是先读取余额再写回，不是原子操作。

### 2.3 显示

侧栏（`AppShell`）显示余额，数据来自 `GET /api/profile` 的 `tokens` 字段。后端请求失败时，前端会直接用 Supabase SDK 读取 `profiles.tokens` 作为兜底。余额变化后，前端派发 `tokensChanged` 事件，通知侧栏刷新。

## 3. 谁可以改余额

**只有后端（Service Role）可以改变能量值余额。** 这条规则由数据库权限保证（`20261001120000_billing_authorization_hardening.sql`），不依赖代码自觉：

| 对象 | 已登录用户（Anon Key + JWT） | 后端 Service Role |
|---|---|---|
| `profiles.tokens`、`daily_streak`、`last_activity_at`、`mastered_questions` | 只读 | 读写 |
| `profiles` 的其他资料字段（简历、`profile_json`、头像、诊断结果等） | 只能改自己的行 | 读写 |
| 插入 `profiles` 行 | 只能插入自己的行，而且不能指定 `tokens`（使用默认值 1000） | 可以 |
| RPC `deduct_user_tokens` | 不能调用 | 可以 |
| RPC `create_interview_session`（扣费金额由参数 `p_token_cost` 决定） | 不能调用 | 可以，后端固定传 300 |

后端写这些字段时必须使用 `lib/supabase.js` 的 `supabase`（Service Role）客户端。用 `supabaseForUser(token)` 写的话会返回 `42501 permission denied`。回归测试是 `backend/test/sql/billing_authorization.sql`。

## 4. 已知问题与风险

| # | 问题 | 影响 | 位置 |
|---|---|---|---|
| 1 | 先检查后扣费，中间没有锁；`addTokens` 不是原子操作 | 并发时可能少扣或少加 | `middleware/tokens.js` |
| 2 | 没有被使用的文案 `profile.energyUsedCv` 写的是"简历提取 (30)"，与实际扣费 50 不一致；页面上实际显示的 `profile.tokenUsageExtract` 是"简历解析 (50)"，是正确的 | 目前不影响用户，但以后误用会显示错误价格 | `locales/*.json` |

已修复（2026-10-01）：模拟充值接口可以随意加余额；用户可以直接修改自己的 `tokens` 和打卡状态；任何已登录用户都能调用 `deduct_user_tokens` 扣别人的余额；用户可以直接调用 `create_interview_session` 并传入 0 来免费创建面试。

如果要接入真实支付，需要新建独立的订单 / 权益模型。成长中心里的 `premiumPreview` 只是展示，不能作为付费资格的依据。
