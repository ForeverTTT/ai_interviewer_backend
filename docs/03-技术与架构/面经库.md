# 面经库

> 状态：现行 · 最后核对：2026-10-09 · 产品说明：[面经库](../01-产品/功能说明/面经库.md)
> 代码：`backend/src/routes/experiences.js`、`backend/src/routes/admin.js`（审核）、`backend/src/routes/notifications.js`（站内通知）、`backend/src/lib/interviewLearning.js`（RAG 检索）、`frontend/src/pages/ExperiencesPage.jsx`、`frontend/src/pages/AdminReviewPage.jsx`、`frontend/src/components/app/NotificationBell.jsx`

## 1. 数据

表 `interview_experiences`：`type`（`internship` 实习 / `campus` 秋招 / `experienced` 社招；旧数据中的 `work` 已迁移为 `internship`，`school` 保留为旧类型「高校录取」，只在「全部」里显示，新面经不能选）、`company`、`location`、`position`、`department`、`date`（`YYYY-MM`）、`language`、`rounds`（每轮的形式、时长、题目 `questions`，以及与题目按下标对应、可选的作者回答 `answers`；RAG 出题时不带回答）。现在每篇面经只记录一轮面试：发布表单顶部填「面试轮次」（如一面、技术面、HR 面）和时长，存为 `rounds[0]`；旧的多轮面经仍按轮展示，编辑时会合并成一轮、`result`（发布表单已不再填写，也不再展示，旧数据保留）、`salary`、`reflection`、`publisher`（发布者的名字或邮箱前缀）、`user_id`，以及：

- `visibility`：`private`（仅自己可见）或 `public`（分享到面经库）
- `review_status`：`none`（私密，不审核）、`pending`、`approved`、`rejected`
- `reward_granted`：是否已发放 +200 能量值；`reviewed_at`：审核时间；`review_note`：拒绝原因（可选，会展示给作者）

RLS：其他人（包括未登录用户）只能读到 `public` 且 `approved` 的面经，作者能读到自己的全部面经。作者只能删除自己还没公开的面经（`review_status` 不是 `approved`）；已收录的面经只能由管理员删除或撤下。新增只能经由后端（service role），客户端不能直接插入。

### 审核与奖励

分享到面经库的面经（发布时直接选，或之后把私密面经提交上去）以 `pending` 状态进入审核。管理员在 `/admin/experiences` 审核：待审核的可以通过或拒绝，已通过的可以撤下，已拒绝的可以改为通过。管理员由后端环境变量 `ADMIN_EMAILS`（逗号分隔）决定，账号邮箱必须已验证；侧栏的「管理 · 面经审核」入口只对管理员显示。

管理员拒绝或撤下时可以填写原因（`review_note`），作者在「我的面经」和通知里都能看到。被拒绝的面经作者可以修改，保存为「分享到面经库」即重新进入 `pending`，旧的拒绝原因会被清掉。

触发器 `handle_experience_review` 负责：

- 改为 `approved` 时给作者加 200 能量值，并把 `reward_granted` 置为 true（每篇只发一次，撤下后再通过也不会重复发）。撤下已通过的面经不会扣回奖励。
- 审核状态变为 `approved` 或 `rejected` 时，往 `user_notifications` 写一条 `experience_review` 通知（公司、岗位、结果、之前的状态、原因、发放的能量值）。
- 重新进入 `pending` 时清空 `review_note`。

在 Supabase 后台直接改 `review_status` 也会触发同样的逻辑。迁移前已存在的面经视为 `public` / `approved` / 已发奖励。

### 站内通知

表 `user_notifications`：`user_id`、`type`、`payload`（jsonb）、`read_at`、`created_at`。只由后端和触发器写入；用户通过 RLS 只能读自己的。前端顶栏的铃铛（`NotificationBell`）显示未读数，打开即全部标为已读；在页面切换和窗口重新获得焦点时刷新。目前没有邮件通知。

## 2. 接口行为

| 接口 | 鉴权 | 行为 |
|---|---|---|
| `GET /api/experiences` | 公开 | 返回已审核通过的公开面经，按时间倒序（**没有分页**） |
| `GET /api/experiences/mine` | 需要登录 | 返回当前用户的全部面经（含私密、审核中、未通过） |
| `POST /api/experiences` | 需要登录 | 用 zod 校验字段；`visibility` 默认 `private`；`public` 时进入审核；没有每日数量限制；提交时不发奖励 |
| `PUT /api/experiences/:id` | 需要登录 | 编辑自己的面经，只允许私密或被拒绝的；`visibility` 为 `public` 时重新进入审核；其他状态返回 409 `NOT_EDITABLE` |
| `POST /api/experiences/:id/submit` | 需要登录 | 把自己的私密面经提交到面经库（改为 `public` + `pending`） |
| `DELETE /api/experiences/:id` | 需要登录 | 只能删除自己还没公开的面经（已收录的返回 409 `NOT_DELETABLE`）；仅当该篇已发过奖励（例如被撤下的）时扣回 200 能量值 |
| `GET /api/admin/me` | 需要登录 | 返回 `{ isAdmin }` |
| `GET /api/admin/experiences?status=` | 管理员 | 按审核状态（`pending` / `approved` / `rejected`）列出面经库投稿，并返回各状态数量 |
| `POST /api/admin/experiences/:id/review` | 管理员 | `{ decision: 'approved' \| 'rejected', note? }`，`note` 只在拒绝时保存 |
| `DELETE /api/admin/experiences/:id` | 管理员 | 删除任意状态的面经库投稿，并通知作者（`experience_deleted`）；不扣回奖励 |
| `GET /api/notifications` | 需要登录 | 最近 30 条通知和未读数 |
| `POST /api/notifications/read` | 需要登录 | 全部标为已读 |

`/api/experiences` 没有使用 `requireAuth` 中间件，而是在处理函数里用 `supabaseForUser(token).auth.getUser()` 自行验证 token；`/api/admin` 和 `/api/notifications` 使用 `requireAuth`。

## 3. 前端

`/experiences` 使用 `AdaptiveLayout`：已登录时显示在 `AppShell` 中，未登录时显示官网布局。页面提供统计卡片、类型筛选（全部 / 实习 / 秋招 / 社招）、全文搜索（企业、岗位、题目、感想），`?mine=true` 只显示自己发布的面经，并在卡片上标出「仅自己可见 / 审核中 / 已收录 / 未通过审核」。发布弹窗里可以选「仅自己可见」或「分享到面经库」；私密面经的卡片上有「分享到面经库」和「编辑」按钮；被拒绝的面经显示拒绝原因和「修改后重新提交」按钮，编辑沿用发布弹窗。筛选和搜索都在前端完成。

## 4. 用作面试题目来源（RAG）

练习模式出题时，`lib/interviewLearning.js` 的 `retrieveExperienceContext` 读取最近 100 篇已审核通过的公开面经，按岗位、JD 关键词匹配和面试官类型排序，取前 4 篇作为出题参考，并在题目的 `source_metadata` 中记录来源。详见[面试流程 · 能力矩阵与 RAG](模拟面试/面试流程.md#103-能力矩阵与-rag)。

因此，用户分享的面经会直接影响其他用户的练习题目。

> `backend/data/knowledge_base/interview_experiences.json` 目前没有被任何代码读取。RAG 使用的是数据库中的 `interview_experiences` 表。

## 5. 已知限制

- 列表接口没有分页，面经增多后响应会越来越大。
- 审核结果只有站内通知，没有邮件。
- 已通过或审核中的面经不能编辑，需要删除后重新发。
- 删除面经时扣回的奖励使用 `deduct_user_tokens`，余额最低扣到 0。
