# 成长中心

> 状态：现行（付费分层未上线） · 最后核对：2026-10-01 · 产品说明：[成长中心](../01-产品/功能说明/成长中心.md) · 设计历程：[成长中心改版方案](../06-决策与方案/进行中/成长中心改版方案.md)
> 代码：`backend/src/routes/growthCenter.js`、`backend/src/lib/growthCenter.js`、`backend/src/lib/offerSprint.js`、`frontend/src/pages/DashboardPage.jsx`、`frontend/src/components/OfferSprintPanel.jsx`
> 测试：`backend/test/growthCenter.test.js`、`backend/test/offerSprint.test.js`

成长中心（`/dashboard`）不保存自己的面试状态，它是**面试事实数据的行动化读模型**：从面试、报告、训练事件和冲刺计划中计算出"今天做什么、结果如何、哪些可以继续"。题目收藏的实现见[题目收藏](题目收藏.md)，报告中准备度的结构见[面试报告](面试报告.md#2-报告结构中的准备度)。

## 1. 数据来源

页面加载时并行发出两个请求：

```text
DashboardPage
 ├─ GET /api/interviews ─────────────► 最近 50 场面试 → 复盘记录、最新复盘、练习次数与时长
 └─ GET /api/growth-center/overview ─► 并行查询 5 项：
       ├─ 最近 20 场「已完成且有报告」的面试 ──► aggregateCareerReadiness ─► readiness（职场胜算）
       ├─ 最近 3 张待复习收藏（置顶优先）    ──► recentCollections
       ├─ 最近 400 条训练事件               ──► summarizeTrainingEvents ─► rhythm（本周天数、连续天数）
       ├─ 当前用户的冲刺计划
       └─ 最近 100 场面试（用于周报时长）
                       └──► syncOfferSprint ─► offerSprint（任务、提醒、里程碑、周报）
```

> **`GET /overview` 有写入副作用**：每次调用都会在 `syncOfferSprint` 中生成或过期本周任务、写入提醒、生成里程碑（都用 Service Role、按 `user_id` 限定，幂等）。所以它不是纯读取接口，不要在高频场景下调用，也不能被缓存层随意重放。

## 2. 职场胜算（五维准备度汇总）

### 2.1 单份报告的准备度：`enrichReportForGrowth`

五个固定维度：`technical`、`experience`、`structure`、`communication`、`strategy`。对每个维度：

1. **报告里有分数**（`careerReadiness.dimensions[].score`）：直接使用，限制在 0–100。
2. **报告里没有分数**：在报告的优势、不足、逐题复盘文字中，按该维度的关键词表（中、英、德）查找匹配句子，按匹配到的条数**推算**：

   ```text
   score = clamp(66 + 优势条数 × 7 − 不足条数 × 9, 35, 92)
   ```

3. **两者都没有**：`score = null`，`status = 'insufficient'`，不显示分数。

每个有分数的维度都附带证据 `{ interviewId, questionIndex, excerpt }`：优先使用报告给出的证据，否则使用匹配到的句子（不足优先）。单份报告的 `assessment`：五个维度都有分数时为 `initial`，否则为 `partial`。

> 第 2 步是基于报告原文的关键词启发式，并不是模型直接打的分。报告 Prompt 已要求模型输出 `careerReadiness`，大多数新报告会走第 1 步；旧报告或模型漏输出时才会走第 2 步。

### 2.2 多份报告的汇总：`aggregateCareerReadiness`

- 输入最多 20 份报告，计算时只用**最近 5 份**。
- 以最新一份报告为"目标"，每份报告的权重为：

  ```text
  weight = 新近度 1 / (1 + 0.35 × 序号)
         × (职位与目标相似度 ≥ 0.5 ? 1.25 : 1)
         × (面试官类型与目标相同 ? 1.15 : 1)
  ```

- 维度分数 = 加权平均；**趋势** = 最新一份与上一份的分数差，至少有两份有分数时才计算，否则为 `null`。
- `overallScore` = 有分数的维度取平均；`assessment`：只有 1 份报告时为 `initial`，2 份及以上为 `established`，没有报告时为 `insufficient`。
- 同时返回 `nextPracticeTask`（来自最新报告）和最多 5 个 `weeklyTasks`（下一题 + 分数最低维度的建议动作）。

> 汇总不区分练习和正式模拟：只要是"已完成且有报告"的面试都会参与。

前端显示的总分优先使用汇总的 `overallScore`；`overview` 失败或汇总没有分数时，才退回读取最新报告中的 `overallScore` / `overall_score` 字段。

## 3. 训练统计

### 3.1 有效训练事件

表 `interview_training_events`，以 `(user_id, dedupe_key)` 去重。只有四种事件：

| 事件 | 由谁写入 | 条件 |
|---|---|---|
| `valid_answer` | 触发器 `record_effective_answer_event`（插入作答后） | 回答非空，每次作答一条 |
| `interview_completed` | 触发器 `record_interview_training_milestones` | `status` 第一次变为 `completed` |
| `effective_duration` | 同上 | `accumulated_seconds` 第一次达到 480 秒（8 分钟） |
| `system_task_completed` | `PATCH /offer-plan/tasks/:id`、`POST /tasks/:id/complete` | 冲刺任务或系统任务完成 |

暂停、浏览、单独写笔记都不会产生事件。练习页离开时会用 keepalive 请求执行服务端 pause，先结算活跃秒数再清空 `active_since`，所以离开页面的时间不会被算进训练时长。

### 3.2 统计口径

| 指标 | 计算位置 | 规则 |
|---|---|---|
| 本周有效天数、连续天数 | 后端 `summarizeTrainingEvents` | 按事件的 `activity_date` 去重；周一为一周开始；今天还没有事件时从昨天往前数连续天数 |
| 有效练习次数 | 前端 | `/api/interviews` 返回的 50 场中，已完成或 `accumulated_seconds ≥ 480` 的场次 |
| 累计有效时长 | 前端 | 同样 50 场的 `accumulated_seconds` 之和；不用计划时长 `duration` 补齐 |

`overview` 失败时，前端会用这 50 场面试自行估算本周天数和连续天数。

## 4. Offer 冲刺计划

### 4.1 计划

表 `growth_offer_plans`，每个用户一行（`user_id` 唯一），通过 `PUT /offer-plan` upsert：

- `target_position` 必填；日期必须是 `YYYY-MM-DD`；`weekly_target_days` 只能是 3、5 或 7。
- `reminder_preferences` 被规范化为 `{ inApp(默认 true), browser(默认 false), email, weeklyReport(默认 true) }`。只有 `GROWTH_REMINDER_EMAIL_OUTBOX_ENABLED=true` 时 `email` 才可能为 true。
- 删除计划时，任务和提醒通过外键级联删除。

### 4.2 阶段：`classifyOfferSprint`

按 **UTC 自然日**计算距 `next_interview_date` 的天数：

| 阶段 | 条件 |
|---|---|
| `setup` | 没有计划 |
| `renew` | 面试日期已过；或没有面试日期但目标 Offer 日期已过 |
| `interview_day` | 0 天 |
| `final48` | 1–2 天 |
| `imminent` | 3–7 天 |
| `focused` | 8–21 天 |
| `foundation` | 超过 21 天，或没有任何日期 |

### 4.3 每周任务：`buildOfferSprintTasks` + `syncOfferSprint`

每个阶段有一组按优先级排好的候选任务：

| 阶段 | 候选任务（按顺序） |
|---|---|
| `foundation` | 还没有正式报告时先做 `baseline`，否则做 `focus_question`；然后 `focus_question`、`review_collection`、`formal_mock`、`weekly_review` |
| `focused` | `focus_question`、`formal_mock`、`review_collection`、`self_intro`、`weekly_review` |
| `imminent` | `formal_mock`、`focus_question`、`review_collection`、`pre_interview_checklist`、`self_intro` |
| `final48` | `pre_interview_checklist`、`self_intro`、`formal_mock`、`review_collection`、`focus_question` |
| `interview_day` | `pre_interview_checklist`、`self_intro`、`review_collection`、`focus_question` |
| `renew` | `weekly_review`、`focus_question`、`review_collection` |

- `focus_question` 来自汇总结果的 `nextPracticeTask`；`review_collection` 用置顶或最新的待复习收藏，没有收藏时换成 `weekly_review`；`pre_interview_checklist` 带上最近 3 张收藏卡。
- 去重后取前 N 个：`weekly_target_days = 3` 时 N = 3，否则 N = 5。
- `task_key = 周一日期 : 类型 : 来源`，同一周同一来源的任务是幂等的。
- 同步时：已完成或已跳过的任务保留，并占用名额；不再需要的 `pending` 任务标记为 `expired`；其余按 `task_key` upsert。
- **今日任务** = 本周第一个 `pending` 任务（按优先级排序）。
- `PATCH /offer-plan/tasks/:id`：只能把 `pending` 改为 `completed` 或 `skipped`；对已完成的任务重复提交会直接返回；`skipped` 和 `expired` 的任务返回 409 `OFFER_TASK_INACTIVE`。完成时写入一条 `system_task_completed` 事件。

### 4.4 提醒：`buildReminderBlueprints`

- 面试前 7 天、2 天、当天的 08:00 UTC，以及每周日 17:00 UTC 的周报提醒；按用户开启的渠道（`in_app` / `browser` / `email`）各生成一条。
- 以 `(user_id, reminder_key, channel)` 去重写入 `growth_offer_reminders`；用户关闭某个渠道后，该渠道仍是 `pending` 的提醒会被标记为 `dismissed`。
- `overview` 只返回 `scheduled_for` 已到期的 `pending` 提醒；`PATCH /offer-plan/reminders/:id` 可以标记为 `read` 或 `dismissed`。
- **邮件提醒只写 outbox**，本服务不发送邮件，需要外部 Worker 认领 `email` 渠道的 `pending` 记录，并回写 `sent` / `failed`（目前没有这个 Worker）。

### 4.5 其他

| 项 | 实现 |
|---|---|
| 恢复提示 `buildRecoveryNudge` | 有计划、今天还没训练、以前训练过、本周天数未达标时出现；有连续天数时为 `continue`，否则为 `restart` |
| 周报 `buildWeeklyGrowthReport` | 本周事件天数、本周面试的有效分钟数、完成的任务数、有趋势的维度变化（没有趋势就不显示变化）、下一题 |
| 里程碑 `syncMilestones` | 首份正式报告、连续 5 天、任一维度趋势 ≥ 15；以 `(user_id, milestone_key)` 幂等写入 |
| `premiumPreview` | 只是展示标记（报告 ≥ 2 份或已完成任务时 `visible`），`existingDataAlwaysAccessible` 恒为 true；**不是付费资格，也不能作为扣费依据** |

## 5. 最新复盘与面试复盘记录

### 5.1 状态到行动

前端按以下顺序判断每场面试的状态（先看真实报告，再看能否恢复，最后看是否在生成中），以兼容状态字段和报告落库时间短暂不一致的历史数据：

| 条件 | 显示 | 主按钮 |
|---|---|---|
| 有报告内容（`report_json` 有内容，或旧的 `report_markdown` 非空） | 报告已就绪 | 查看完整报告 → `/interview/:id/report` |
| `mode = practice` 且 `status ∈ (draft, active, paused)` | 未完成 / 已暂停 | 继续练习 → `/interview/:id` |
| `mode = formal` 且 `status ∈ (draft, active, paused)` | 自动触发 finalize，卡片立即显示"生成中" | 无 |
| `status = finalizing` 或 `finalize_status = processing` | 生成中 | 无 |
| `status = completed` 且没有报告 | 暂无报告 | 查看报告状态 → `/interview/:id/report` |
| 其他 | 已结束 | 无 |

- **最新复盘**选取顺序：正在生成的 → 有报告的 → 已完成的 → 最新一场。
- **筛选**：`reports` = 有报告、生成中或已完成；`continue` = 可以继续的练习。
- 正式模拟的自动 finalize 以空 `messages` 调用，服务端会回退到已持久化的 `transcript_json`；同一场面试在本页只会触发一次。这一行为是否合理，见[问题与想法](../问题与想法.md)。

### 5.2 "继续练习"的不变量

- 路由带原 `interviewId`，**不调用** `POST /api/interviews`，不扣费；
- 详情读取以 `id + user_id` 校验归属；
- 练习从持久化的题目、作答、提示、笔记、checkpoint 和计时恢复；已暂停的练习进入后仍保持暂停，只有显式 resume 才继续计时；
- `POST /api/interview-sessions/:id/resume` 对正式模拟返回 `409 FORMAL_RESUME_FORBIDDEN`。

### 5.3 删除

`DELETE /api/interviews/:id`，前端二次确认后调用。注意：`interviews_backup` 中的备份不会随之删除，见[数据库参考](../04-参考/数据库.md#面试主链路)。

## 6. 接口与权限

接口清单见 [API 参考 · 成长中心](../04-参考/API.md#成长中心-apigrowth-center)。

| 表 | 用户直接访问（RLS） | 写入方 |
|---|---|---|
| `growth_offer_plans` | 读写自己的行 | 后端以用户身份 upsert / delete |
| `growth_offer_tasks`、`growth_offer_reminders`、`growth_milestones` | 只读 | 后端 Service Role，所有更新都带 `user_id` 条件 |
| `interview_training_events` | 只读 | 触发器、后端 Service Role |

所有接口都先执行 `requireAuth`，`user_id` 一律取自认证上下文，不接受请求体传入。

## 7. 已知限制

- `GET /overview` 带写入副作用（见第 1 节）。
- 列表接口 `/api/interviews` 最多返回 50 场，练习次数和累计时长会低估老用户的数据；后续应改成在数据库侧计算的专用接口。
- `interviews` 列表使用 `select('*')`，负载偏大。
- 计划保存了 `timezone`（默认 `Europe/Berlin`），但阶段、周边界和提醒时间都按 **UTC** 计算，没有使用这个字段；训练事件的 `activity_date` 也是 UTC 日期，而前端兜底统计用的是浏览器本地日期。
- 页面上"本周节奏"的目标天数固定显示为 `/ 5`，没有使用计划里的 `weekly_target_days`。
- `POST /tasks/:taskId/complete` 接受任意 `taskId`，每个新 ID 都会写入一条 `system_task_completed` 事件，用户可以借此刷出有效训练天数和"连续 5 天"里程碑（不涉及能量值）。
- 维度分数在报告缺少显式评分时使用关键词启发式推算（见 2.1）。
- 邮件提醒没有投递 Worker。

## 8. 回归检查

修改成长中心后至少确认：

- 后端：`npm test`（覆盖五维证据与样本门槛、趋势、按日去重、冲刺阶段在 21 / 7 / 2 / 0 天的边界、周任务上限、48 小时清单、提醒渠道、周报不虚构趋势）；
- 单份报告不显示趋势，没有证据的维度不显示分数；
- 继续练习进入原 `interviewId`，不新建面试、不扣费；
- 每周任务不超过 3 或 5 项，已完成的任务不会被刷新覆盖；
- 关闭提醒渠道后不再出现该渠道的提醒；未开启邮件 outbox 时不生成 email 提醒；
- 前端 `npm run build` 通过，中、英、德文案文件是合法 JSON。
