## 1. 背景与目标

### 现状

- 项目已有面向**排障**的观测能力：`logStructured()` 输出结构化 JSON 日志，Cloud Run 自动收集到 Cloud Logging；面试过程另有 `interview_events` 表记录 finalize、Gemini 调用、实时语音延迟等诊断事件。
- 但没有面向**产品分析**的数据：不知道用户从哪里来、在哪一步流失、哪些功能真正被使用、能量值怎么被消耗。
- `CookieBanner` 只把"同意 / 拒绝"写进 localStorage，没有任何代码读取它；点右上角 X 关闭时不保存任何状态，下次打开页面横幅会再次出现。

### 目标

1. 能回答核心产品问题：激活、漏斗、留存、面试完成率、功能渗透、能量值消耗。
2. 为后续的付费设计、改版评估、渠道投放提供数据依据。
3. 符合 GDPR：数据留在欧盟、最小化采集、客户端行为需用户同意、可删除。
4. 尽量复用现有基础设施，第一期**不新增数据库表、不做 migration、不接第三方 SDK**。

### 非目标

- 不做会话录屏、热力图、A/B 实验平台（见 [§7 演进路线](#7-演进路线)）。
- 不替代 `interview_events`：它继续负责面试诊断，本方案只负责产品分析。

## 2. 数据全景

本项目的数据来自三个来源，其中后端日志又分两类：

| | ① 前端埋点 | ②a 后端请求与排障日志 | ②b 后端业务事件 | ③ 业务数据库 |
|---|---|---|---|---|
| 是什么 | 用户在浏览器里的行为 | 每次请求、报错、Gemini 调用 | 有业务结果的关键动作 | 产品运行必需的真实数据 |
| 例子 | 页面浏览、按钮点击、配置页卡在哪步、中途离开、报告看了多久 | `auth_succeeded`（userId + path）、`express_error`、`finalize_*`、`live_turn_timing` | 面试开始 / 完成、报告生成、扣能量值 | 用户资料、简历、面试与报告、收藏、面经、能量值余额 |
| 存放位置 | 经后端写成日志 → BigQuery | Cloud Logging（默认 30 天） | 日志 → BigQuery | Supabase (Postgres) |
| 回答的问题 | 怎么用、在哪流失 | 系统稳不稳定 | 做了什么（权威） | 是谁、有什么 |
| 现状 | 已实现 | 已有 | 已实现 | 已有 |
| 需要用户同意 | 是 | 否 | 否 | 否 |

关联键：

- `userId`：三方共有，主关联键；
- `interviewId`：面试相关的埋点、日志、`interviews` 表共有；
- `anonymousId`：只存在于前端埋点，用户登录后的第一条事件同时带上 `anonymousId` 和 `userId`，把注册前的行为归到该用户。

## 3. 总体架构

```
浏览器 track() / page()
   │ 已同意 Cookie 才采集；批量发送（5 秒 / 10 条 / 页面隐藏）
   ▼
POST /api/ux-events ──┐
                      ├──► backend/src/lib/analytics.js
后端业务代码          │      • 事件白名单 + properties 白名单
trackServerEvent() ───┘      • logStructured('info', 'analytics.<name>', …)
                                     │
                                     ▼
                     Cloud Logging（Cloud Run 自动收集）
                                     │ Log Sink：jsonPayload.event =~ "^analytics\."
                                     ▼
                     BigQuery 数据集 analytics（europe-west1，分区保留 13 个月）
                                     │
                       SQL 视图 / 定时汇总表
                                     │
                 BigQuery Studio · Looker Studio 看板 · Google 表格
```

### 选型理由

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **A. 日志 → BigQuery（采用）** | 复用现有 `logStructured` 和 Cloud Run 日志；无 migration；数据在自己的 GCP 项目、欧盟区域；几乎零成本；SQL 能力强 | 不能直接和 Supabase 业务表 JOIN；看板需自己搭 | **第一期采用** |
| B. Supabase 新建 `analytics_events` 表 | 可直接和业务表 JOIN | 需要 migration 和生产 Schema 审核；分析型查询会占用业务数据库资源 | 暂不采用 |
| C. PostHog EU Cloud 等第三方 | 现成漏斗、留存、录屏、A/B | 多一个数据处理方，需签 DPA；数据不在自己手里；SDK 体积和拦截问题 | 作为后期演进选项 |

"不能直接 JOIN 业务表"的应对：埋点时把分析需要的维度直接写进事件（例如 `interview_started` 带上 mode、语言、面试官类型）。确有需要时再做 Supabase → BigQuery 定时同步（见 §7）。

## 4. 关键决策

| 决策 | 理由 |
|---|---|
| 所有事件写成 `analytics.*` 日志，props 存为 JSON 字符串 | 复用 `logStructured` 和 Cloud Run 日志；BigQuery Sink 自动推断列类型，固定顶层字段 + 字符串 props 可以避免类型冲突导致写入失败 |
| 后端维护事件和字段白名单 | 隐私规则不依赖前端自觉；前端多传的字段直接丢弃 |
| 前端分两层：全局自动采集 + 少量业务语义事件 | 前端代码约 1.7 万行，逐个手写埋点不现实；自动采集覆盖所有页面（包括以后新增的），业务事件补充自动采集看不出的含义 |
| 文本框只记长度，长文字视为内容不记，用户内容区域加 `data-track-mask` | "尽量记录所有行为"与"不采集用户内容"同时满足 |
| 有业务结果的动作以后端事件为准 | 不受广告拦截和 Cookie 拒绝影响，数字准确 |
| 接口命名为 `/api/ux-events`，单独限流 | 避开广告拦截关键词；埋点请求不占用户正常调用接口的额度 |
| Cookie 横幅：拒绝后不再反复询问，提供"Cookie 设置"入口 | 原文案"继续使用即表示同意"不是有效同意；反复询问已拒绝的用户会被视为诱导同意 |
| 轻反馈只有 👍/👎 和预设原因，走登录接口、不依赖 Cookie 同意 | 用户主动提交，不属于行为追踪；没有自由文本，埋点里不会出现用户写的内容 |
| 不在反馈中关联或保存用户的简历、JD、生成结果（2026-10-04） | 目的限制和用户预期；德国简历常含照片、出生日期、国籍等敏感信息。曾考虑"点 👎 后用户勾选同意分享内容"的方案，暂不实施 |


## 5. 隐私与合规

| 项目 | 做法 |
|---|---|
| 合法性依据 | 服务端事件：功能运行所需，使用假名化 userId，按正当利益处理。客户端事件：需用户同意 |
| 同意管理 | 修复 `CookieBanner`；提供随时撤回的入口；未同意不生成任何标识、不发送任何请求 |
| 数据最小化 | 数据红线由后端白名单强制执行，见[技术文档](../../03-技术与架构/通用机制/埋点与数据分析.md#数据红线) |
| 存储位置 | BigQuery `europe-west1`，Cloud Logging 同项目 |
| 保留期 | BigQuery 分区 13 个月自动过期；Cloud Logging 原始日志 30 天 |
| 删除请求 | 在 BigQuery 执行 `DELETE FROM … WHERE userId = @id`。步骤见[数据分析运维](../../05-运维/数据分析.md#6-删除用户数据) |
| 访问控制 | 只为需要分析的人授予 `analytics` 数据集的只读权限，不授予整个项目 |
| 隐私政策 | 待编写，见 §6 |

## 7. 演进路线

按需推进，不预先建设：

| 触发条件 | 做法 |
|---|---|
| 需要按业务数据分组分析（例如按简历评分、按能量值余额） | 每天定时把 Supabase 中需要的表的**非敏感字段**同步到 BigQuery（`analytics.dim_users`、`analytics.dim_interviews`） |
| 需要会话录屏、热力图、现成漏斗 UI | 接入 PostHog EU Cloud，由 `frontend/src/lib/analytics.js` 同时转发；签署 DPA，录屏默认遮蔽所有输入 |
| 需要 A/B 实验 | 先在后端做简单的按 userId 哈希分组，分组信息写进事件的 `experiment` 字段；量大后再用 PostHog 的实验功能 |
| 需要实时告警（例如完成率突然下降） | 基于 `analytics.*` 日志建 Cloud Logging 日志指标和告警 |
| 上线付费 | 新增 `checkout_started`、`payment_succeeded`、`subscription_changed` 等服务端事件，以支付回调为准 |
