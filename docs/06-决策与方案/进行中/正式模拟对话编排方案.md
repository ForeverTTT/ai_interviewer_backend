# 正式模拟对话编排方案

> 状态：**已决策：采用方案 A+（2026-10-01）**，第 0 步已完成两轮测量，越权提问率仍未达标，修正方案待确认（见第 10.1、10.2 节） · 编写日期：2026-10-01 · 关联：[模拟面试 · 面试流程](../../03-技术与架构/模拟面试/面试流程.md)、[agent与Prompt](../../03-技术与架构/模拟面试/agent与Prompt.md)、[实时语音与TTS · Gemini Live](../../03-技术与架构/模拟面试/实时语音与TTS.md#11-gemini-live-实时语音)、[问题与想法](../../问题与想法.md)

本文记录让正式模拟的**对话流程**变得可控的方案：先比较了 A、B、C 三种做法，最终采用综合 A 与 B 长处的 **A+**。第 3–6 节是比较过程，第 7 节是采用的设计，第 10 节是迁移步骤，第 11 节汇总所有已确认的决定。

## 0. 最终设计摘要（2026-10-01 确认）

| 方面 | 决定 | 详见 |
|---|---|---|
| 总体方案 | **A+：后端定题，Live 自由表达**。后端决定问什么、何时追问 / 换题 / 收尾，并评估回答；Live 用自己的话提问，自己处理澄清和复述，收到新指令前不换题 | 第 7.1–7.3 节 |
| 验收标准 | 听感停顿 P90 不超过现状 +1.5 秒；越权提问率不超过 5% | 第 10 节第 4 步 |
| 题位计划 | 正式模拟按题型**分块**、不循环（练习模式保留现在的循环排列）。HR：经历 25% → 行为 75%；技术：整场是项目技术深挖，不单设经历块；综合：经历 → 技术 → 行为（行为约 28%，放在最后） | 第 7.7 节 |
| 出题依据 | 以简历为基础：简历拆成锚点，按"与 JD 的相关度 × 经历类型系数"加权分配题位（work 1.0 / project 0.8 / academic 0.6），相关度 < 0.3 的经历不问 | 第 7.8 节 |
| 降级阶梯 | 答不上来时：① 项目深挖 → ② 通用案例 → ③ 八股（行为题只有 ① → ②）；**降级不算追问** | 第 7.8 节 |
| 追问 | 上限按难度：简单 1 次、中等 2 次、困难 3 次（整道题合计）；评分低于阈值（简单 50 / 中等 65 / 困难 80）或缺少关键证据，满足任意一个就追问；追问作为原题的延续记录 | 第 7.7 节 |
| 收尾 | 不留反问环节 | 第 7.7 节 |
| 回答是否说完 | 由 Live 判断：语音活动检测 + 函数调用信号（函数调用待第 0 步验证） | 第 7.7 节 |
| 时间紧张 | 先不再追问；再紧张就不降级、跳过当前块剩下的题位，保证每个题型块（技术面为权重靠前的项目）至少问到一道 | 第 7.7 节 |
| Live 的语气 | 寒暄和鼓励按面试官性格区分；任何性格都不评价、不透露分数、不自行换题 | 第 7.7 节 |
| 数据库 | 只需一个向后兼容的 migration（追问作答），其余状态存在 checkpoint 的 JSON 中 | 第 10 节 |
| 闲置代码 | LangGraph、`data/prompts/`、SSE / TTS 兼容通道**保留**，编排器只借用其分析与追问思路 | 第 10 节第 6 步 |
| 暂不处理 | "离开页面即结束面试"的问题，以后单独改 | 第 11 节 |


> **术语**：本文中的"阶段"指题位的题型类别（经历深挖 / 技术 / 行为）。开场固定是自我介绍；之后正式模拟按面试官类型**分块**排列题型：HR 面是经历 → 行为，技术面整场是项目技术深挖，综合面是经历 → 技术 → 行为，详见第 7.7 节（练习模式保留循环排列）。

## 1. 背景

### 1.1 状态分两层

| 层 | 管什么 | 现状 |
|---|---|---|
| 业务状态 | 面试状态、截止时间、题目、作答、`state_version`、幂等 | **已经管好了**：PostgreSQL + RPC，与 LangGraph 无关。Live 每完成一轮，`interviewLiveSocket.js` 都会把这一轮写进库里，并检查截止时间 |
| 对话流程状态 | 当前题位及其题型（开场之后按面试官类型排列经历深挖、技术、行为题，见第 7.7 节）、下一题问什么、要不要追问、每个回答的质量、难度升降 | **正式模拟里基本没有管理**，全部交给 Gemini Live 的一段系统提示词 |

练习模式已经由后端控制流程：后端出题 → 前端发 `[PRACTICE_CONTROL]` 控制消息 → Live 只朗读这道题 → 其余时间不把 Live 的输出转发给浏览器 → 候选人提交后由后端评估。

### 1.2 正式模拟现在的问题

正式模拟的流程由 `buildSystemInstruction` 里的一段话决定："计划大约 N 道核心题，根据回答追问，在截止前结束，一次只问一个问题"。由此带来：

1. **题量和阶段不可控**："大约 N 题"只是一句建议，问多少、问什么阶段都由模型决定。
2. **没有逐题评估**：不调用任何评估逻辑，所以 **Adaptive 难度在正式模式中实际不生效**，报告只能在结束后一次性评估。
3. **题目记录不准**：Live 每说完一段话，就被记成一道 `interview_questions`，寒暄、追问、复述都会被算成题。
4. **不可测试**：流程藏在模型内部，没法写单元测试，也没法针对某个阶段单独调优。
5. **面试官类型只靠提示词约束**：练习模式出题后会校验题型（HR 面不能出技术题），正式模式没有这个校验。

### 1.3 已经可以复用的部分

| 能力 | 位置 | 说明 |
|---|---|---|
| 题量与阶段计划 | `agents/utils.js` 的 `getMaxQuestions`、`buildInterviewPlan` | 按时长和面试官类型生成阶段序列 |
| 按阶段出题 | `lib/interviewLearning.js` 的 `generateInterviewQuestion` | 带难度、面试官类型、能力矩阵、RAG；会校验题型是否属于该阶段和类型；正式模式超时为 45 秒 |
| 回答评估 | `analyzePracticeAnswer` | 返回 0–100 分、优势、不足和证据 |
| 难度升降 | `adaptDifficulty` | ≥85 升一级，≤55 降一级 |
| 备用题 | `buildFallbackInterviewQuestion` | 模型失败时按阶段给出本地备用题 |
| 状态动作 | RPC `apply_interview_action`（`question` / `attempt`） | 原子写入题目和作答 |
| 只让 Live 朗读指定内容 | `interviewLiveSocket.js` 的 `practiceSpeechAllowed` 闸门 | 练习模式已经在用 |
| 正式模式中途隐藏反馈 | `interviewSessions.js` | HTTP 响应里清除 `feedback_json` |
| LangGraph 分析与路由 | `agents/interviewGraph.js` 的 `analyze_answer`、`routeQuestionEdge` | 只挂在 SSE 兼容通道上，目前闲置 |

## 2. 目标与非目标

**目标**

- 正式模拟的题量、阶段顺序、面试官类型约束由代码保证；
- 每个回答都有评估，Adaptive 难度在正式模式中真正生效；
- 只有真正的题目才写入 `interview_questions`，报告的逐题复盘更准确；
- 编排逻辑可以写单元测试；
- 候选人感受到的对话节奏不明显变慢。

**非目标**

- 不改练习模式（它已经由后端编排）；
- 不改报告生成；
- 不在本方案里决定"离开页面就结束面试"的问题（见第 11 节）；
- 不更换 Live 模型。

## 3. 方案 A：后端编排，Live 只负责听和说

### 3.1 流程

```text
候选人回答（Live 实时转写）
  → Live turn_complete
  → 后端：写入作答（apply_interview_action: attempt）
  → 后端编排器 decideNextTurn：
        评估回答（隐藏分数）→ 调整难度 → 按计划决定：追问 / 下一阶段 / 收尾
        → 生成下一句要说的内容（generateInterviewQuestion，或追问模板）
  → 写入题目（apply_interview_action: question，只有真正的题目才写）
  → 服务端直接向 liveSession 注入控制消息："只朗读这一句"
  → Live 朗读 → 等待候选人回答
```

Live 的输出闸门在正式模式下默认关闭，只有服务端注入的控制消息才会打开一次（与练习模式相同，区别是由**服务端**注入，而不是由前端发送）。

### 3.2 改动范围

| 位置 | 改动 | 规模估计 |
|---|---|---|
| 新增 `backend/src/lib/formalOrchestrator.js` | `decideNextTurn({ workspace, answer })` → `{ action: 'follow_up' \| 'next_question' \| 'close', utterance, stage, difficulty, evaluation }`。复用计划、出题、评估、难度和备用题逻辑；定义追问规则（例如每个阶段最多追问 1 次，评估分数低于阈值或缺少证据时追问） | 新文件，约 200–300 行，外加单元测试 |
| `backend/src/live/interviewLiveSocket.js` | 正式模式在被编排时：默认关闭输出闸门；`turn_complete` 后调用编排器；由服务端注入控制消息；忽略客户端发来的以 `[PRACTICE_CONTROL]` 开头的文本；系统提示词改成"只朗读控制消息里的内容"；截止时间到了不再出新题（已有逻辑） | 修改约 100–150 行 |
| `backend/src/lib/interviewLearning.js` | 增加一个正式模式的评估函数（或给 `analyzePracticeAnswer` 加参数），评估结果只写入 `interview_attempts.feedback_json` 和能力证据，不返回给客户端 | 小 |
| `frontend/src/components/ChatInterface.jsx`、`useGeminiLiveInterview.js` | 显示"面试官思考中"的状态；正式模式下打字作答走同一条作答路径，而不是直接发给 Live | 小到中 |
| 面试配置 | 在 `graph_state_json.config` 中记录 `orchestration: 'backend' \| 'live'`（是 JSON 字段，**不需要 migration**），保证进行中的面试不受切换影响 | 小 |
| 环境变量 | `FORMAL_ORCHESTRATION=live\|backend`，默认 `live`，用于灰度发布 | 小 |
| 测试 | 编排器单元测试（题量、阶段、追问上限、类型约束、截止、备用题）；SQL 测试不需要改 | 中 |
| 文档 | 面试流程、面试房间、agent与Prompt、产品文档模拟面试 | 小 |

### 3.3 延迟估计

> 以下是**估计值**，没有实测，迁移第 0 步会先测量真实数据。

| 环节 | 现在 | 方案 A |
|---|---|---|
| 候选人说完 → Live 判定这一轮结束 | 约 0.5–1 秒（Live 的语音活动检测） | 相同 |
| 写入作答 | 不在关键路径上（异步） | 约 0.05–0.2 秒（需要同步完成） |
| 评估 + 决定 + 出题 | 无 | 合并成一次 Flash-Lite 调用约 **1.5–3 秒**；分两次调用约 2.5–5 秒 |
| 注入控制消息 → Live 开始发声 | Live 直接接话，约 0.5–1 秒 | 约 0.5–1 秒 |
| **候选人说完 → 听到下一句** | **约 1–2 秒** | **约 2.5–5 秒** |

缓解办法（可以叠加使用）：

1. **合并调用**：评估和出题放在同一次模型调用里，只等一次。
2. **先回应、再提问**：`turn_complete` 后先让 Live 说一句简短的过渡语（例如"好的，谢谢"），在这段时间里后端计算，下一句准备好后再注入。听感上的停顿可以压到 1–2 秒。
3. **预先生成**：候选人回答时，就用当前阶段先生成下一道主问题；回答结束后只需要决定"追问还是用预先生成的题"。
4. 使用 `GEMINI_PRACTICE_MODEL`（Flash-Lite）这类低延迟模型做编排。

### 3.4 成本

每一轮额外增加 1 次（合并后）到 2 次文本模型调用。Flash-Lite 的单次成本远低于 Live 的音频成本，预计对整场面试的总成本影响很小，需要在第 0 步一并测量。

### 3.5 风险

- 延迟是主要风险，必须在灰度阶段对比实测数据；
- 过渡语如果处理不好，可能听起来很机械；
- 闸门关闭期间 Live 仍会生成内容（只是不转发），这部分成本还在，需要确认能否通过系统提示词让它保持沉默。

## 4. 方案 B：LangGraph 重新做"导演"

### 4.1 流程

和方案 A 一样，区别在于 `decideNextTurn` 由 LangGraph 实现：每轮 `turn_complete` 后，执行一次 `route_turn → analyze_answer → ask_explore / ask_technical / ask_behavioral / give_feedback`，节点的输出不再流式返回给前端，而是作为要朗读的内容注入 Live。

### 4.2 改动范围

在方案 A 的 Live 侧、前端、配置、灰度改动之外，还需要：

| 位置 | 改动 | 规模估计 |
|---|---|---|
| `backend/src/agents/interviewGraph.js` | 从"流式聊天"改为"产出下一句话"：去掉 SSE 相关部分；状态从数据库的 workspace 加载，而不是从 `transcript_json` 推断；节点输出要写成规范化的题目和作答 | 修改约 200–300 行 |
| Prompt 模板 `data/prompts/*.md` | 现有模板是为文本聊天写的（例如"≤50 字"），需要改成适合朗读，并统一使用面试官类型和难度指令 | 中 |
| 两套出题逻辑 | 练习用 `interviewLearning`，正式用 LangGraph，需要决定是否合并；不合并的话，同一件事会有两种实现 | 需要决策 |
| 测试 | LangGraph 节点和路由目前没有单元测试，需要补 | 中到大 |

### 4.3 延迟估计

LangGraph 的 `analyze_answer` 和 `ask_*` 是**两次串行的**模型调用：分析器用主模型 `GEMINI_MODEL`（温度 0.3），出题节点用的是 Live 模型的文本模式（`createGeminiLiveTextModel`，超时 45 秒）。估计合计 **3–6 秒**，比方案 A 的合并调用慢。方案 A 的缓解办法同样适用，但"合并成一次调用"需要改图的结构。

### 4.4 优缺点

- 优点：复用现有的分析器、路由和阶段 Prompt；对话流程以图的形式表达，比较直观。
- 缺点：LangGraph 当前和数据模型不一致，需要先对齐；会和练习模式形成两套出题逻辑；串行调用更慢；没有现成的测试。

## 5. 方案 C：保留 Live 自主对话，用函数调用上报状态

### 5.1 流程

在 `ai.live.connect` 的配置中声明几个工具，让 Live 在对话中调用：

| 工具 | 作用 |
|---|---|
| `ask_question({ stage, questionText, questionType })` | 提出一道正式题目前调用；后端校验阶段和题型，写入 `interview_questions` |
| `advance_stage({ to })` | 进入下一阶段；后端检查是否符合计划 |
| `end_interview({ reason })` | 主动收尾 |

后端在工具的返回值里告诉模型"已经问了几题、还剩多少时间、下一阶段是什么"，必要时拒绝不合规的调用（比如 HR 面提出技术题）。

### 5.2 改动范围

| 位置 | 改动 | 规模估计 |
|---|---|---|
| `backend/src/live/interviewLiveSocket.js` | 在连接配置中声明工具；处理 `toolCall` 消息并回传 `toolResponse`；只有调用了 `ask_question` 才写题目 | 修改约 100–150 行 |
| 系统提示词 | 要求每道正式题目都先调用 `ask_question` | 小 |
| 测试 | 工具处理函数可以单测；但模型是否按要求调用，只能靠真实对话验证 | 中 |

需要先确认：当前使用的 `gemini-3.1-flash-live-preview` 是否支持函数调用，以及调用期间音频是否会被阻塞。

### 5.3 延迟估计

只有调用工具的那几轮才增加一次往返，后端处理约 0.1–0.3 秒，加上模型等待返回的时间，估计每次约 **+0.2–0.5 秒**。其他轮次不受影响。

### 5.4 优缺点

- 优点：改动最小，几乎不增加延迟，对话最自然。
- 缺点：**决策权仍然在模型手里**。模型可能忘记调用工具，题量和阶段只是"可观测"，并不是"可控"；也无法做到逐题评估和 Adaptive 难度（除非再增加评估工具，那就会接近方案 A 的延迟）。

## 6. 哪种更像真实面试

A 和 B 的结构其实相同，都是"后端决定、Live 发声"，框架本身不决定真实感。真实感取决于下面四点：

| 真实面试的特征 | A：后端编排 | B：LangGraph 编排 | C：函数调用 |
|---|---|---|---|
| **对话节奏**：答完很快得到回应 | 较好：一次合并调用 | 较差：两次串行调用，停顿 3–6 秒，最容易出戏 | 最好：Live 直接接话 |
| **追问质量**：抓住回答里的细节往下问 | 需要补强：`generateInterviewQuestion` 偏向"出下一道题" | 较好：分析器记录分析笔记，`ask_explore` 专门围绕简历追问 | 好，但不可控 |
| **结构化覆盖**：按能力项有计划地问 | 代码保证 | 代码保证 | 模型自觉 |
| **应对非回答的发言**：候选人说"能再说一遍吗""你是指……吗"，或者闲聊 | **会退步** | **会退步** | 好 |

最后一行是 A 和 B 共同的最大风险。现在 Live 自主对话，候选人请它复述、澄清时能很自然地接住。如果改成"后端出稿、Live 逐字朗读"，并且把候选人的每句话都当作回答去评估、再出下一题，对话就会变得机械，甚至答非所问。

结论：**最像真实面试的做法是在 A 的基础上，让 Live 保留自由表达的能力**，同时吸收 B 的追问逻辑。这就是下面的方案 A+。

## 7. 方案 A+：后端定题，Live 自由表达

### 7.1 分工

| 谁 | 负责 |
|---|---|
| 后端编排器 | 当前该问哪道题（题目意图）、是否追问、何时进入下一个题位、何时收尾；评估回答；调整难度；记录题目和作答 |
| Gemini Live | 用自然的口吻把题目问出来（可以换说法，不必逐字照读）；自己处理澄清、复述、简短确认和闲聊；**在收到下一条导演指令之前不能换题** |

### 7.2 流程

```text
后端注入导演指令 [DIRECTOR]：当前题目意图、题位与题型、可以如何措辞、禁止事项
  → Live 用自己的话问出来（输出闸门在正式模式下保持打开）
  → 候选人发言 → Live turn_complete
        ├─ Live 立即自然回应：澄清 / 复述 / 一句简短确认（"明白，谢谢"），不提出新问题
        └─ 后端并行：意图判断 + 评估 + 决定下一步（一次合并调用）
              ├─ 意图 = 请求澄清、闲聊 → 不记作答，等候选人继续
              ├─ 意图 = 回答 → 记作答 → 追问 / 下一题 / 收尾
              └─ 注入下一条导演指令
```

### 7.3 与方案 A 的区别

| | A | A+ |
|---|---|---|
| Live 的输出闸门 | 正式模式默认关闭，只放行控制消息 | 正式模式保持打开 |
| Live 怎么说 | 逐字朗读后端给出的句子 | 根据导演指令用自己的话问 |
| 澄清、复述 | 需要后端识别后再生成回应，慢且容易出错 | Live 直接处理 |
| 写入 `interview_questions` 的内容 | 后端生成的句子 | 后端的**题目意图**；Live 的实际措辞保存在消息里 |
| 编排器的输出 | `{ action, utterance, ... }` | `{ intent: 'answer' \| 'clarification' \| 'other', action, questionIntent, stage, difficulty, evaluation }` |
| 追问 | 规则 + 出题函数 | 把 LangGraph 分析器的"分析笔记"和 `ask_explore` 的追问思路合并进编排器 |

### 7.4 延迟

候选人说完后，Live 会立刻做出确认或澄清（与现在一样约 1–2 秒）；后端在这段时间里并行计算，1.5–3 秒后注入下一题。**听感上的停顿接近现状**，最多在确认语和下一题之间多出约 1 秒。

### 7.5 改动范围

在方案 A 的基础上：

| 位置 | 额外改动 |
|---|---|
| `formalOrchestrator.js` | 输出增加意图判断；合并 LangGraph 分析器的分析笔记和经历深挖的追问规则 |
| `interviewLiveSocket.js` | 定义 `[DIRECTOR]` 导演指令协议并由服务端注入；正式模式不再关闭输出闸门；系统提示词改为"按导演指令提问，可以自由措辞和处理澄清，未收到新指令不得换题，不做评价" |
| 监控 | 新增"越权提问率"：Live 在没有新指令时自行提出新问题的比例（可以抽样，用一次轻量分类调用检测 Live 的输出） |
| 数据库 migration | `interview_attempts` 增加 `kind`、`prompt_text`；`apply_interview_action` 允许正式模式下有上限的 `follow_up` 作答；报告生成和题目收藏读取追问 |
| Live 连接配置 | 调整 `realtimeInputConfig.automaticActivityDetection`；如果支持，声明 `answer_complete` 函数并处理 `toolCall` |
| 简历锚点提取 | 面试开始时一次模型调用，从 `resume_snapshot` 提取锚点并按权重分配题位，结果写入 checkpoint；在会前准备阶段完成 |
| 题位计划 | 为正式模拟**新增**题位规划函数（例如 `buildFormalInterviewPlan`），使用"题型块 + 比例"的配置，技术面的题位由简历锚点生成。**练习模式保留现在的 `buildInterviewPlan` 和 `planPattern` 循环排列，不受影响**（2026-10-01 确认） |

### 7.6 风险

- **Live 可能不听指令自行换题**：用系统提示词约束确认语的长度和内容，并用越权提问率监控；如果比例偏高，可以退回方案 A 的闸门做法。
- **需要确认 Live 是否支持在会话中途追加指令**：当前代码用 `sendRealtimeInput({ text })` 发送控制消息，练习模式已经验证过这种方式可以让 Live 按指令说话；导演指令是否同样可靠，需要在第 0 步一并测试。
- 意图判断出错（把回答当成澄清，或者反过来）：在合并调用里同时返回置信度，置信度低时按"回答"处理，并在报告中保留原话。

### 7.7 下一题机制（2026-10-01 确认的规则）

**原则：规则交给代码，判断交给模型。** 追问、换题、收尾由代码按规则决定；回答好不好、追问抓哪个缺口、下一题问什么内容，由一次模型调用给出。

#### 面试开始时：生成大纲

创建正式模拟时按时长和面试官类型生成**题位计划**（练习模式保留现在的循环排列，不受影响）：开场固定是自我介绍，之后的题位**按题型分块排列，不循环**——一种题型的题位全部问完，再换下一种（2026-10-01 确认）。题位数量沿用 `getMaxQuestions`（约每 2.5 分钟一题）。

| 面试官类型 | 题型块顺序 | 各块比例 | 15 分钟示例（开场之后共 7 个题位） |
|---|---|---|---|
| HR | 经历深挖 → 行为（含动机） | 经历约 25%、行为约 75%（已确认） | 经历 ×2 → 行为 ×5 |
| 技术 | **只有一种题型：项目技术深挖**。题位按简历锚点的权重分给各个项目，一个项目连续问完再换下一个；候选人答得上来就一直围绕项目经历深挖，答不上来才按降级阶梯转到通用案例和八股（第 7.8 节） | 按锚点权重 | 项目 A ×4 → 项目 B ×2 → 项目 C ×1 |
| 综合 | 经历深挖 → 技术 → 行为 | 行为约 28%（放在最后，**不提前**），其余由经历和技术平分（已确认） | 经历 ×3 → 技术 ×2 → 行为 ×2 |

技术面**不单独设经历深挖块**（已确认）：整场都是项目技术深挖。同一个项目的连续题位中，第一题问整体与个人贡献，之后问技术实现、取舍和遇到的问题。没有可用的简历时，技术面的题位从降级阶梯第 ② 层（通用案例）开始。

> 现状对照：现在的 `buildInterviewPlan` 对 HR 和技术面按 `config/interviewerTypes.js` 的 `planPattern` **循环**排列（例如技术面"技术 → 经历 → 技术 → 案例 → 技术"），对综合面用单独的算法（经历和技术交替，行为在最后），配置中综合面的 `planPattern` 实际没有被使用。实施时为正式模拟新增"题型块 + 比例"的规划，技术面的题位由简历锚点生成；练习模式继续使用 `planPattern` 循环排列。

计划和进度存进数据库的 checkpoint，刷新或断线后从这里继续：

| 状态 | 含义 |
|---|---|
| 当前题位及其题型 | 例如"第 3 个题位，技术题" |
| 当前题已追问次数 | 与追问上限比较 |
| 当前题目意图 | 交给 Live 的"要问什么" |
| 当前难度 | Adaptive 模式下随回答升降 |
| 已问过的题、已覆盖的能力项 | 避免重复，优先考察未覆盖的能力 |

#### 每一轮：候选人说完之后

```text
Live 判定候选人说完（见下方"回答是否说完"）
  ├─ Live：立刻自然回应（澄清 / 复述 / 一句简短确认），不提新问题
  └─ 后端（同时进行）：一次模型调用 → 意图（回答 / 请求澄清 / 闲聊）+ 隐藏评分 + 缺口 + 追问焦点或下一题内容
       → 按下表规则决定下一步 → 注入导演指令
```

| 顺序 | 条件 | 结果 |
|---|---|---|
| 1 | 不是回答（请求澄清、闲聊） | 状态不变，Live 已经接住，等候选人继续 |
| 2 | 剩余时间不够再问一题 | 收尾（时间紧张时的收紧规则见下方"时间紧张时自动收紧"） |
| 3 | 评分低于该难度的追问阈值（简单 50、中等 65、困难 80），**或者**模型判断回答缺少关键证据（例如没有具体例子、个人贡献或结果），且当前题的追问次数未达上限 | 追问，针对模型指出的缺口 |
| 4 | 其他情况 | 下一题：进入计划中的下一个题位，按该题位的题型出题 |
| 5 | 计划中的题都已问完 | 收尾（**不留反问环节**） |

#### 已确认的规则

| # | 问题 | 决定 | 实现方式 |
|---|---|---|---|
| 1 | 追问几次 | **按难度调整** | 每道题的追问上限：简单 1 次、中等 2 次、困难 3 次；自适应按当前生效的难度取值 |
| 2 | 追问算不算新题 | **作为原题的延续** | 追问的回答记为同一道题的后续作答，报告里在原题下展示"追问 → 回答"。需要修改数据库函数，见下方 |
| 3 | 收尾是否留反问环节 | **不留** | 计划问完或时间不够时，Live 直接致谢并结束 |
| 4 | 怎么判断回答说完了 | **由 Live 判断** | 见下方 |
| 5 | 追问条件 | **评分和证据两个都算** | 两个条件满足任意一个就追问：评分低于阈值（简单 50、中等 65、困难 80，难度越高要求越严；自适应按当前难度），或者模型判断缺少关键证据 |
| 6 | Live 能否寒暄和鼓励 | **看面试官性格** | 见下方"不同性格下 Live 的自由度" |

**规则 2 需要一个 migration。** 现在的 `apply_interview_action` 在正式模式下会拒绝同一题的第二次作答（`attempt_number > 1`）。需要新增一个向后兼容的 migration：

- `interview_attempts` 增加 `kind`（`answer` / `follow_up`，默认 `answer`）和 `prompt_text`（追问的意图）；
- 正式模式下允许 `kind = 'follow_up'` 的后续作答，次数不超过该题的追问上限；普通重答仍然禁止；
- 报告生成和题目收藏读取作答时，把同一题的追问一并带上。

**规则 4 的实现方式。** "由 Live 判断"有两层：

1. **语音活动检测**：调整 Live 的 `realtimeInputConfig.automaticActivityDetection`（例如加长 `silenceDurationMs`、降低结束灵敏度），让候选人的短暂停顿不会被判定为说完。这一层不依赖模型理解内容。
2. **模型判断内容是否完整**：在系统提示词里要求 Live 在候选人明显没说完时只做简短的鼓励（"嗯，请继续"），并通过函数调用 `answer_complete()` 告诉后端这一轮的回答已经完整；后端只在收到这个信号后才评估和推进。没有收到信号的轮次，转写会拼接到下一轮。

第 2 层依赖 `gemini-3.1-flash-live-preview` 支持函数调用，需要在第 0 步验证。如果不支持，就只用第 1 层，再由后端的合并调用兜底判断"是否说完"。

#### 时间紧张时自动收紧（2026-10-01 确认）

每次决定下一步之前，先比较剩余时间和剩下的题位：

```text
剩余题位数 R，剩余时间 T，每题预估时长 t（默认 2.5 分钟，与 getMaxQuestions 的估算一致；第 0 步实测后调整）
```

| 档位 | 条件 | 做法 |
|---|---|---|
| 正常 | `T ≥ R × t × 1.5`（剩下的题位留有追问和降级的余量） | 按正常规则追问和降级 |
| 紧张 | `R × t ≤ T < R × t × 1.5` | **先减少追问**：不再追问；降级仍然可以 |
| 很紧张 | `T < R × t` | **答不上来时不降级，直接进入下一个题位**；并**跳过当前题型块剩下的题位，直接进入下一个块**，保证计划里的每个题型块至少问到一道（技术面只有一种题型，改为跳到下一个项目，保证权重靠前的项目都至少问到一道） |

- 档位每轮重新计算，时间宽裕后可以恢复。
- 第 1 条规则"剩余时间不够再问一题就收尾"仍然优先：连一个题位都放不下时直接收尾。
- 这一机制在三种面试官类型下都生效；对综合面最重要，因为它的行为题排在最后，最容易被时间挤掉。
- 1.5 这个余量系数是默认值，灰度阶段根据实际数据调整。

#### 不同性格下 Live 的自由度

在所有性格下，Live 都可以回答澄清、复述题目，都**不能**评价回答好坏、透露分数或自行换题。寒暄、鼓励和确认语按面试官性格区分，与 `config/interviewerStyles.js` 中现有的性格设定保持一致：

| 性格 | 开场寒暄 | 回答后的回应 | 鼓励 | 追问时的语气 |
|---|---|---|---|---|
| 专业严谨 `balanced` | 简短、礼貌 | 一句简短的中性确认（"明白""好的"），不夸奖 | 不主动鼓励 | 平和、聚焦缺口 |
| 温和鼓励 `supportive` | 稍长、温暖，帮候选人放松 | 可以先点出回答里一个具体的优点，再继续 | 可以简短鼓励（"没关系，慢慢想"），不过度夸奖、不替候选人回答 | 建设性的措辞 |
| 严厉压力 `demanding` | 极简，直接进入正题 | 尽量不回应，或一个字的确认 | 不鼓励 | 直接指出模糊、矛盾或缺少证据之处 |
| 深度分析 `analytical` | 简短 | 可以用一句话准确复述候选人的要点，作为追问的铺垫 | 不主动鼓励 | 追问推理、取舍、假设和个人贡献 |

这些规则写进导演指令的"可以 / 不可以"部分，由后端按面试的 `interviewer_style` 生成，不需要候选人或前端传入。

#### 下一题的内容

按第 7.8 节的"以简历为基础"策略确定题目意图，再复用 `generateInterviewQuestion` 生成具体内容：输入当前题位的题型、简历锚点与降级层级、难度（Adaptive：≥85 升一级，≤55 降一级）、面试官类型（不合规的题型会被拦截并重新生成）、能力矩阵、最近几题的回答与缺口、相关面经、已问过的题。模型失败时用该阶段的本地备用题。候选人回答期间，后端预先生成计划中的下一道主问题；回答结束后只需要决定"追问，还是直接使用预生成的题"。

#### 交给 Live 的导演指令

```text
[DIRECTOR]
题位：第 3/7 个，技术题    类型：追问（第 1/2 次，中等难度）
要问的内容：他如何保证支付回调不会被重复处理；如果提到数据库约束，可以问并发情况
可以：用自己的话问；回答候选人的澄清；简短回应
不可以：评价回答；收到下一条指令前换题；提出反问环节
```

数据库记录的是题目意图（追问记在原题之下），Live 的实际措辞作为对话消息另存。

### 7.8 出题策略：以简历为基础（2026-10-01 确认）

**原则：面试以简历为基础提问；与招聘要求越相关的经历问得越多，不相关的经历不问；项目上答不上来时再降级到通用题。**

现状：只有"经历深挖"题会用到简历；技术题的出题指令是"出一道岗位相关的技术或案例题"，与简历无关。`buildCompetencyMatrix` 只是在 JD 和简历中做关键词匹配，比较粗。

#### 1. 面试开始时：把简历拆成锚点

用一次模型调用，从 `resume_snapshot` 中提取项目和经历作为**锚点**：

| 字段 | 说明 |
|---|---|
| `anchorId` | 锚点编号 |
| `kind` | `work`（工作 / 实习 / 学生工）、`project`（个人或团队项目）、`academic`（课程、论文、学术项目） |
| `title`、`role` | 名称、本人角色 |
| `techStack` | 用到的技术 |
| `claims` | 简历中声称的成果和数据 |
| `jdRelevance` | 与 JD 要求的相关度（0–1），附上对应的 JD 要求 |

锚点存入 checkpoint（JSON，不需要 migration）。提取可以在候选人进入会前准备页时开始，不占用面试时间。

#### 2. 按权重分配题位

每个锚点的权重：

```text
权重 = jdRelevance × 类型系数
类型系数（默认）：work 1.0，project 0.8，academic 0.6
```

- **相关度低于阈值（默认 0.3）的锚点直接排除，不提问**；
- 以简历为基础的题位按权重**成比例分配**给剩下的锚点（最大余数法取整）。与招聘最相关的工作经历分到的题位最多；
- 同一个锚点可以出现在不同的题型块里：例如综合面中，项目 A 在经历块里问整体贡献，在技术块里再问技术实现；技术面中，同一个项目的题位连续排列；
- 所有锚点都被排除时，视为"没有可用的简历"，见第 5 小节。

以上系数和阈值已确认作为默认值（2026-10-01），灰度阶段可以根据实际效果调整。

题型决定从哪个角度问：

| 题型 | 以简历为基础的问法 |
|---|---|
| 经历深挖 | "你在 X 项目里具体负责什么？结果如何？" |
| 技术 | "X 项目里为什么选 Redis？缓存一致性怎么处理的？" |
| 行为（HR） | "X 项目里有没有遇到分歧？你是怎么推进的？" |

#### 3. 答不上来时：沿降级阶梯下降

| 层级 | 技术题 | 行为题 |
|---|---|---|
| ① 项目深挖 | 围绕锚点的实现、取舍和个人贡献 | 围绕锚点中的具体经历 |
| ② 通用案例 | 与岗位相关的通用案例或场景题，例如"设计一个秒杀系统的库存扣减" | 通用 STAR 行为题 |
| ③ 基础知识（八股） | 岗位相关技术的基础原理，优先选锚点里出现过的技术，例如"Redis 有哪几种持久化方式" | — |

区分两种情况：

- **答得不好**（评分低于阈值或缺少证据）→ 在**同一层**追问；
- **答不上来**（明确说不会 / 没做过 / 不记得，或答非所问）→ **降一级**，不再追问这一层。

编排器的合并调用需要额外返回 `canAnswer`（能否回答）判断。

**降一级不算追问**（2026-10-01 确认）：降级不占用追问次数。追问次数按**整道题合计**（简单 1 次、中等 2 次、困难 3 次），不论发生在哪一层；降级次数由阶梯本身限定，技术题最多降 2 次（① → ② → ③），行为题最多 1 次。因此每种难度都能降到最底层，简单难度也会问到八股。

一道题最多的问答轮数（首问 + 降级 + 追问）：

| 难度 | 技术题 | 行为题 |
|---|---|---|
| 简单 | 1 + 2 + 1 = 4 轮 | 1 + 1 + 1 = 3 轮 |
| 中等 | 1 + 2 + 2 = 5 轮 | 1 + 1 + 2 = 4 轮 |
| 困难 | 1 + 2 + 3 = 6 轮 | 1 + 1 + 3 = 5 轮 |

这只是上限，大多数题不会走满。时间不够时由第 7.7 节的"时间紧张时自动收紧"规则处理。

#### 4. 与面试官类型的关系

| 面试官类型 | 以简历为基础的题型 | 降级阶梯 |
|---|---|---|
| HR | 经历深挖、行为 | 行为题：① → ②（通用 STAR） |
| 技术 | 项目技术深挖（整场围绕简历项目） | ① 项目深挖 → ② 通用案例 → ③ 八股；不降级时一直问项目经历 |
| 综合 | 三种都有 | 按题型分别使用上面的阶梯 |

#### 5. 没有可用的简历时

没有上传简历，或者所有锚点都与 JD 不相关时，题目直接从第 ② 层（通用案例 / 通用 STAR）开始，按 JD 出题，技术题仍可降到 ③。面试配置页已经提示"不使用简历时，面试官不会围绕简历追问"。

#### 6. 记录

题目的 `source_metadata` 记录 `anchorId`、`fallbackLevel`（1 / 2 / 3）和降级原因。报告可以据此说明"项目层面答不上来，降级到通用案例后的表现"，比单纯给一个低分更有用。

## 9. 建议

**采用方案 A+。** 它保留了 A 的可控性（流程由代码决定、逐题评估、Adaptive 难度、题目记录准确、可以测试），同时保留了 Live 在澄清、复述和语气上的自然表现，听感上的停顿最接近现状，是四种方案里最像真实面试的。B 的长处（分析笔记、围绕简历追问）合并进编排器即可，不需要重新启用整套 LangGraph。

如果第 0 步发现 Live 无法可靠遵守导演指令，就退回方案 A（关闭闸门、逐字朗读），再用"先确认、再提问"的方式缓解停顿。

### 10.1 第 0 步结果（2026-10-01）

**① 线上延迟埋点**：已上线（`da402e1b`）。正式模拟每一轮写入一条 `live_turn_timing` 事件，`duration_ms` 是"候选人最后一段转写 → 面试官第一段声音"的毫秒数。需要等有用户做正式模拟后才有数据。

**② 合并调用耗时**（`scripts/benchmarkOrchestration.js`，"意图 + 隐藏评分 + 下一步"一次调用，每类 5 次）：

| 模型 | 完整回答 | 请求澄清 | 很短的回答 | JSON 成功率 | 意图判断 |
|---|---|---|---|---|---|
| Flash-Lite（`gemini-3.5-flash-lite`） | 中位数 1.10 秒 / P90 1.28 秒 | 0.81 / 0.90 秒 | 0.97 / 1.01 秒 | 15/15 | 全部正确 |
| 主模型（`gemini-3.7-flash`） | 超时 | 429 | 429 | 0/15 | — |

结论：编排用 Flash-Lite，一次调用约 1 秒，低于方案估计的 1.5–3 秒。**风险**：测试用的 Key 连续调用十几次后就被限流（429），上线前需要确认生产 Key 的配额，否则多人同时面试时编排调用可能失败（失败时用备用题，不会卡住）。

**③④ Live 遵守导演指令、函数调用**（`scripts/testLiveDirector.js`，20 场 × 6 轮 = 120 轮，三种语言 × 四种性格轮换，候选人发言以文本发送）：

| 指标 | 结果 | 目标 |
|---|---|---|
| 越权提问率（没有导演指令的轮次中自行提出新问题） | **16.5%**（13/79） | ≤ 5%，**未达标** |
| 导演指令的题目按意图问出 | 100% | — |
| 读出导演指令原文 / 说错语言 | 0% / 0% | — |
| 发送文本 → Live 开始出声 | 中位数 0.59 秒，P90 0.90 秒 | — |
| 函数调用是否被接受 | 支持 | — |
| `answer_complete`：回答说完时调用 | 60% | — |
| `answer_complete`：澄清或没说完时误调用 | 1.3% | — |

越权按性格分布：严厉压力 35%（7/20）、深度分析 20%（4/20）、专业严谨 5%、温和鼓励 5%。13 次中有 2 次是"请继续说"一类的鼓励被分类器误判，真实比例略低。2 次"评价回答"都出现在温和鼓励性格，属于第 7.7 节允许的"点出一个优点"。

**原因**：`config/interviewerStyles.js` 的性格提示词本身包含追问要求（专业严谨："证据不足时追问"；严厉压力："明确指出模糊之处，要求具体行动和数据"；深度分析："追问推理、取舍和实现细节"），与导演指令"不得自行提问"冲突，模型优先服从性格设定。

**测试的局限（2026-10-01 发现）**：这次测试的系统提示词里**没有简历和 JD**，只在导演指令里提到项目名。线上正式模拟会带上完整简历（最多 2.5 万字）和 JD（最多 1.5 万字）。Live 掌握简历后更容易自己追问其他项目或技术，所以 16.5% 很可能**低估**了真实的越权率；"您指的是哪个项目"这类澄清也没有测到。此外，候选人发言以文本发送，没有测到语音停顿；剧本只有一个技术题场景。

**由此暴露的设计缺口：A+ 模式下 Live 应该看到多少简历和 JD**（待决定）：

| 做法 | Live 看到什么 | 好处 | 风险 |
|---|---|---|---|
| ① 全量 | 与现状相同：完整简历 + 完整 JD | 澄清最自然 | 信息越多越容易自行提问 |
| ② 摘要 | 职位、JD 核心要求、简历锚点列表（每个一句话） | 能回答"哪个项目"一类澄清，信息量可控 | 细节问题可能答不上 |
| ③ 只给当前项目 | 系统提示词不放简历，每条导演指令附当前锚点详情和对应的 JD 要求 | 越权诱因最少 | 候选人提到其他项目时 Live 不了解 |

倾向：**② + ③**（系统提示词放摘要，导演指令附当前锚点详情），需要用测试数据确认。

**下一步**：

1. 为编排模式写一版**只保留语气、去掉追问要求**的性格提示词，追问力度改由导演指令控制；重跑时**加上样例简历和 JD**（含与 JD 高度相关的工作经历、相关项目、无关经历），并对比上下文做法 ① 与 ② + ③，剧本加入"您指的是哪个项目"的澄清；
2. 规则 4（回答是否说完）调整为：Live 调用 `answer_complete` 时立即推进；没调用时由后端的合并调用判断是否说完。仍以 Live 为主，但不会因为漏调而卡住；
3. 上线前确认生产 Gemini Key 的配额。

### 10.2 第 0 步第 2 轮结果（2026-10-01）

针对第 1 轮的局限，加入真实 JD（SAP「AI Developer @ Signavio」和「AI Product Management」两个学生工岗位）和两份虚构简历（各含高度相关的工作经历、相关项目、无关经历），剧本增加"您指的是哪个项目"和"提到无关经历"两轮。三组对照（`scripts/testLiveDirectorContext.js`，每组 24 场 × 7 轮）：

- **G0**：现有性格提示词 + 全量简历 / JD；
- **G1**：只保留语气的性格提示词 + 全量简历 / JD；
- **G2**：只保留语气的性格提示词 + 系统提示词放摘要，导演指令附当前项目详情。

测试中途免费档 Gemini Key 的每日额度（每个模型 500 次）耗尽，第 16–24 场作废。以下只统计有效的第 1–15 场（每组 15 场）。完整数据和全部被标记的原文见 [附件：第 2 轮测试报告](附件/正式模拟编排-第0步第2轮测试报告.md)。

| 指标 | G0 | G1 | G2 |
|---|---|---|---|
| 越权提问率 | 10.8%（8/74） | 8.0%（6/75） | 6.7%（5/75） |
| 导演题按意图问出 / "哪个项目"答对 | 100% / 100% | 100% / 100% | 100% / 100% |
| 提到无关经历时顺着去问 | 6.7% | 0% | 0% |
| `answer_complete` 该调用时调用 / 误调用 | 80% / 1.3% | 70% / 0% | 63% / 1.3% |
| 发送 → 首段声音（中位数 / P90） | 558 / 910 ms | 558 / 677 ms | 547 / 714 ms |

**结论**：

1. 只保留语气的性格提示词有效（10.8% → 8.0%，严厉压力 14.3% → 0%）；摘要式上下文（G2）比全量（G1）略好，但差距只有 1 次违规，统计上分不出高下。三组都**未达到 5% 的目标**。
2. 违规集中在**回答结束、没有新导演指令的空档**（尤其是剧本最后一轮），以及**中文**（G0 24%、G2 16%）。
3. **新发现的严重问题**：有 4 次 Live 模仿导演指令格式，**编造并念出** `[DIRECTOR] …`，都发生在空档期。上线前必须解决。
4. 人工复核：大部分"越权"是真越权（主动问"最强技能""有没有考虑别的方案"、转到其他项目）；"评价回答"大多来自温和鼓励性格，属于允许范围；严厉压力说"这和岗位无关"是否算违规待定。

**下一步修正**（待确认后再测）：

1. 不再用文本标记 `[DIRECTOR]` 传指令，改为通过 `answer_complete` 的函数返回值下发下一步；漏调时由后端另行推送；
2. 服务端过滤：输出转写中出现 `DIRECTOR` 字样时立即打断，不再转发音频；
3. 消除空档：回答结束时下一条指令已准备好（预先生成）；没有新指令时只做一句确认并保持安静；
4. 中文场景单独加强提示词并单独测试；
5. 确认生产环境的 Gemini Key 是否为付费档（免费档每个模型每天 500 次，现有服务已有被限流的风险）。

## 11. 决定汇总与待处理事项

已确认（2026-10-01）：

- **采用方案 A+**；验收标准：听感停顿 P90 不超过现状 +1.5 秒，越权提问率不超过 5%；
- 追问上限按难度调整：简单 1 次、中等 2 次、困难 3 次，自适应按当前难度；
- 追问条件：评分低于阈值（简单 50、中等 65、困难 80）或缺少关键证据，满足任意一个就追问；
- Live 的寒暄和鼓励按面试官性格区分（见第 7.7 节）；
- 追问作为原题的延续记录；
- 收尾不留反问环节；
- 回答是否说完由 Live 判断（语音活动检测 + 函数调用信号，见第 7.7 节）；
- 简历锚点使用默认参数：类型系数 work 1.0 / project 0.8 / academic 0.6，相关度低于 0.3 的经历不提问（灰度阶段再根据数据调整）；
- 时间紧张时自动收紧：先不再追问；再紧张就不降级、跳过当前块剩下的题位，保证每个题型块（技术面为权重靠前的项目）至少问到一道（见第 7.7 节）；
- 正式模拟的题位按题型**分块**排列，不循环：HR 经历 25% → 行为 75%；技术面整场是项目技术深挖，不降级就一直问项目经历，不单独设经历深挖块；综合面经历 → 技术 → 行为（行为约 28%），行为题**不提前**；
- 练习模式保留现在的循环排列，题位分块只用于正式模拟；
- 闲置代码（LangGraph、`data/prompts/`、SSE / TTS 兼容通道）保留，不删除；编排器只借用 LangGraph 的分析与追问思路；
- 以简历为基础出题：按与招聘要求的相关度和经历类型加权分配题位，不相关的经历不问；答不上来时按"项目深挖 → 通用案例 → 八股"降级，降级不算追问，追问次数按整道题合计（见第 7.8 节）。

仍待处理：

1. **与"离开页面即结束"的关系**（已约定以后再改，不阻塞本方案）：如果以后支持正式模拟断线后继续（见[问题与想法](../../问题与想法.md)），编排器需要从数据库恢复到当前题位。A 和 A+ 天然支持（状态都在数据库里），C 需要额外处理。
