## 2. 部署架构

```text
push 到 main / 手动 workflow_dispatch
                 │
                 ▼
        GitHub Actions production
                 │
        npm ci → npm test
                 │
                 ▼
  GitHub OIDC → Workload Identity Federation
                 │
                 ▼
       获取短期 Google access token
                 │
                 ▼
    GitHub Runner 执行 docker build
                 │
                 ▼
  推送带 Git SHA 标签的 Artifact Registry 镜像
                 │
                 ▼
       更新现有 Cloud Run 服务
                 │
                 ▼
 /api/health 校验 commit === GitHub SHA
```

镜像格式：

```text
europe-west1-docker.pkg.dev/aiinterviewer-491711-7b1cf/cloud-run-source-deploy/interview-backend:<git-sha>
```

当前方案由 GitHub Runner 直接构建 Docker 镜像，不使用 Cloud Build，也不使用 Cloud Run
源码暂存桶。因此部署账号不需要项目级 Cloud Build 或 Cloud Storage 权限。

## 3. 工作流触发与并发

工作流在以下情况触发：

- push 到 `main`，且提交不只是 README 或后端技术文档变更
- GitHub Actions 页面手动执行 `workflow_dispatch`

以下 docs-only 变更通过 `paths-ignore` 排除，不会重复部署生产服务：

- `README.md`
- `docs/**`

代码、依赖锁文件、Dockerfile、部署工作流及其他运行相关文件的 `main` 更新仍会触发部署。

工作流使用 `cloud-run-production` concurrency group，且 `cancel-in-progress: false`。同一时间只允许
一个生产部署执行；新的发布不会中途取消正在部署的版本。

GitHub job 绑定 `production` Environment，超时时间为 30 分钟。工作流只申请：

```yaml
permissions:
  contents: read
  id-token: write
```

`id-token: write` 仅用于 GitHub OIDC，无需保存长期 Google Service Account JSON key。

## 4. 发布步骤

1. Checkout 仓库。
2. 安装 Node.js 22。
3. 在 `backend/` 执行 `npm ci`。
4. 在 `backend/` 执行 `npm test`；测试失败立即停止，不构建或更新 Cloud Run。
5. 校验 GitHub `production` Environment 的变量和 Secret 是否齐全。
6. 通过 WIF 将 GitHub OIDC 身份映射为后端部署服务账号，并获取短期 access token。
7. 登录区域 Artifact Registry。
8. 使用 `backend/` 构建上下文及 `backend/Dockerfile` 构建镜像，并以完整 Git SHA 作为镜像标签。
9. 推送镜像。
10. 使用 `google-github-actions/deploy-cloudrun@v3` 更新现有 Cloud Run 服务。
11. 合并写入 `APP_COMMIT_SHA` 与 `APP_DEPLOYED_AT`。
12. 请求部署输出 URL 的 `/api/health`，确认 `status=ok` 且 `commit` 等于本次 GitHub SHA。

Cloud Run 当前部署参数：

| 参数 | 值 |
|---|---|
| Execution environment | Gen 2 |
| Port | `8080` |
| CPU | `1` |
| Memory | `512Mi` |
| Min instances | `0` |
| Max instances | `2` |
| Concurrency | `20` |

工作流不会修改服务的公开访问 IAM 策略；`--allow-unauthenticated` 不在自动部署参数中。

## 5. GitHub Production Environment

仓库 `Settings → Environments → production` 必须包含：

| 类型 | 名称 | 当前用途 |
|---|---|---|
| Variable | `GCP_PROJECT_ID` | `aiinterviewer-491711-7b1cf` |
| Variable | `GCP_REGION` | `europe-west1` |
| Variable | `CLOUD_RUN_SERVICE` | `interview-backend` |
| Secret | `GCP_WORKLOAD_IDENTITY_PROVIDER` | WIF Provider 完整资源名 |
| Secret | `GCP_SERVICE_ACCOUNT` | GitHub 后端部署服务账号 |

Secret 值不得写入 README、技术文档、日志或源码。检查配置时只列出 Secret 名称，不输出值。


Provider 条件同时限制仓库与分支：

```text

```

当前部署账号权限：

| 绑定范围 | 角色 | 用途 |
|---|---|---|
| 项目 | `roles/serviceusage.serviceUsageConsumer` | 调用已启用的 Google Cloud API |
| 单个 Cloud Run 服务 `interview-backend` | `roles/run.developer` | 更新该服务和创建 revision |
| 单个 Artifact Registry 仓库 `cloud-run-source-deploy` | `roles/artifactregistry.writer` | 推送后端镜像 |
| Cloud Run 运行账号 | `roles/iam.serviceAccountUser` | 部署时继续使用现有运行身份 |
| 部署账号自身 | `roles/iam.workloadIdentityUser` | 允许受限 GitHub OIDC 身份模拟部署账号 |

部署账号没有项目级 `Editor`、`Cloud Run Admin`、Cloud Build Editor 或 Storage Admin 权限。

Cloud Run 运行账号为：

```text
557559701677-compute@developer.gserviceaccount.com
```

运行账号与部署账号职责不同：运行账号供容器运行时访问所需云资源，部署账号只负责发布。

## 7. 生产环境变量与 Secret

自动部署使用 `env_vars_update_strategy: merge`，只更新：

- `APP_COMMIT_SHA`
- `APP_DEPLOYED_AT`

以下业务配置继续由 Cloud Run 环境变量或 Secret Manager 管理，不由 GitHub 工作流覆盖：

- `SUPABASE_URL`
- `SUPABASE_SERVICE_ROLE_KEY`
- `GEMINI_API_KEY`
- `GEMINI_MODEL`
- `GEMINI_LIVE_MODEL`
- `GEMINI_LIVE_VOICE`
- `FRONTEND_URL`

任何新增的生产 Secret 都应在 Cloud Run 或 Secret Manager 中配置，不得提交 `.env`、OAuth client
secret 或 Service Account JSON 文件。

## 8. 发布验证

成功发布后，健康检查应类似：

```json
{
  "status": "ok",
  "service": "InterviewDE API",
  "commit": "<完整 Git SHA>",
  "revision": "interview-backend-xxxxx",
  "deployedAt": "<UTC ISO 时间>"
}
```

验收要求：

- GitHub Actions 所有步骤成功。
- `/api/health` 返回 HTTP 200。
- `status` 为 `ok`。
- `commit` 与工作流对应的 GitHub SHA 完全一致。
- Cloud Run 最新 ready revision 获得 100% 流量。
- 生产前端 bundle 中的 API 地址指向 `europe-west1` 服务。

首次验证通过的自动部署版本：后端提交 `d7f0f77`，Cloud Run revision
`interview-backend-00007-h27`。该值只作为部署链路上线记录，当前版本以健康接口为准。

## 9. 失败行为与排查

| 失败阶段 | 影响 | 排查重点 |
|---|---|---|
| `npm ci` / `npm test` | 不触碰 Cloud Run | 依赖锁文件、测试日志 |
| OIDC 登录 | 不触碰 Cloud Run | Environment Secret、Provider 条件、仓库和分支名 |
| Docker build | 不触碰 Cloud Run | Dockerfile、依赖安装、构建日志 |
| Docker push | 不触碰 Cloud Run | Artifact Registry 仓库与 writer 权限 |
| Cloud Run deploy | 通常保留上一 ready revision | `run.developer`、运行账号 impersonation、容器启动日志 |
| 部署后健康验证 | 新 revision 可能已经接流量 | 立即检查健康接口、Cloud Run revision 和应用日志，必要时回滚 |

历史上 `gcloud run deploy --source` 会额外要求 Cloud Storage 暂存桶权限。当前工作流已经改为镜像部署，
不要为了修复部署而重新授予项目级 Storage 权限。

## 10. 回滚

优先回滚到上一个已验证的 Cloud Run revision，不要删除失败 revision：

```powershell
gcloud run revisions list `
  --project=aiinterviewer-491711-7b1cf `
  --region=europe-west1 `
  --service=interview-backend

gcloud run services update-traffic interview-backend `
  --project=aiinterviewer-491711-7b1cf `
  --region=europe-west1 `
  --to-revisions=<previous-ready-revision>=100
```

回滚后重新访问 `/api/health`，确认 `commit` 和 `revision` 对应预期旧版本。修复代码后正常 push 到
`main`，由自动部署恢复到新版本。

## 11. 数据库发布边界

Supabase migration 不属于此 Cloud Run 自动部署流程。数据库 Schema 变更必须单独审核、备份并执行，
不能因为应用 push 到 `main` 而自动修改生产数据库。
