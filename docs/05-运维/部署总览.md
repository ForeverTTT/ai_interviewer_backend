# 部署总览

> 状态：现行 · 最后核对：2026-10-01

## 部署源

**本仓库（`ForeverTTT/ai_interviewer_backend`）是前后端唯一的正式部署源。** 前端源码由原独立前端仓库 `ForeverTTT/ai_interviewer_frontend` 的 `6b8d11df` 同步而来，经过验证可以构建出与原线上版本相同的资源。原前端仓库现在只做构建检查，不再部署。新的前端改动请直接在本仓库的 `frontend/` 中修改，避免两个仓库再次分叉。

## 三条发布线

| 对象 | 触发条件 | 工作流 | 目标 | 文档 |
|---|---|---|---|---|
| 后端 | push 到 `main`，且改动**不只**涉及 `README.md`、`docs/**`、`frontend/**`、Firebase 工作流；也可以手动触发 | `.github/workflows/deploy-cloud-run.yml` | Cloud Run `interview-backend` | [后端部署](后端部署.md) |
| 前端正式站 | push 到 `main`，且改动涉及 `frontend/**` 或该工作流本身 | `.github/workflows/firebase-hosting-merge.yml` | Firebase Hosting `live` 频道 | [前端部署](前端部署.md) |
| 前端 PR 预览 | 同仓库分支发起的 PR，改动涉及 `frontend/**` | `.github/workflows/firebase-hosting-pull-request.yml` | Firebase Hosting 预览频道 | [前端部署](前端部署.md#pr-预览) |
| 数据库 | **不自动执行** | 无 | Supabase 生产库 | [数据库迁移发布](数据库迁移发布.md) |

只改 `docs/` 的提交不会触发任何部署。

## 发布顺序

一个改动同时涉及多层时，按以下顺序发布：

1. **数据库 migration**：先人工审核并执行，必须向后兼容当前线上的后端；
2. **后端**：合并到 `main` 后自动部署，确认 `/api/health` 的 `commit` 已经更新；
3. **前端**：与后端在同一次 push 中时，两条工作流会并行执行。如果前端依赖新的后端接口，要么分两次合并，要么让前端在接口缺失时能够降级。

## 发布后检查

| 检查项 | 方法 |
|---|---|
| 后端版本 | `GET https://interview-backend-557559701677.europe-west1.run.app/api/health`，确认 `commit` 等于本次的 SHA（工作流会自动检查） |
| 前端版本 | 工作流会比较线上 `index.html` 引用的入口 JS 文件名是否与本次构建一致 |
| CORS | 在生产前端登录后调用一次接口 |
| Schema | 如果后端调用了新的 RPC，确认没有出现 `PGRST202` |

## 回滚

| 对象 | 方法 |
|---|---|
| 后端 | 把 Cloud Run 流量切回上一个 revision，见[后端部署 · 回滚](后端部署.md#10-回滚) |
| 前端 | 在 Firebase 控制台的 Hosting 发布记录中回滚，或者 revert 提交后重新 push |
| 数据库 | 没有自动回滚，需要另写一个反向 migration，所以 migration 要尽量做到只增不删 |
