# 数据库迁移发布

> 状态：现行 · 最后核对：2026-10-01

Supabase migration **不属于** Cloud Run 自动部署流程。push 到 `main` 不会修改生产数据库，Schema 变更必须单独审核、备份后再执行。表和 RPC 的清单见[数据库参考](../04-参考/数据库.md)。

## 为什么不自动执行

- 应用代码可以通过切换 revision 秒级回滚，Schema 变更通常做不到；
- 一次错误的 migration 可能影响所有用户的数据；
- 后端和数据库的发布顺序需要人来判断（见下方"兼容性"）。

## 流程

### 1. 编写

- 在 `backend/supabase/migrations/` 中新建 `YYYYMMDDHHMMSS_<说明>.sql`，**不要修改**已经在生产执行过的文件。
- 新表要开启 RLS 并写好策略；`security definer` 函数要校验 `auth.uid()`，并且只授予必要的角色。
- 尽量只增不删：先加新列 / 新函数，等代码不再使用旧的之后，再用另一个 migration 删除。

### 2. 本地验证

```bash
cd backend
npx supabase db reset                          # 从零执行全部 migration 和 seed
npx supabase db lint --local --level warning
npm test
```

如果改动涉及面试状态机或 RPC，再运行事务化验收脚本（见[测试](../02-开发指南/测试.md#数据库事务化验收)）。

### 3. 审核

PR 里单独说明：

- 新增或修改了哪些表、列、函数、策略；
- 是否向后兼容**当前线上的**后端代码；
- 是否会锁表或改写大量数据，预计耗时多久；
- 回退方案（反向 SQL）。

### 4. 备份

执行前在 Supabase 控制台确认最近的自动备份可用；高风险变更先手动导出受影响的表。

### 5. 执行到生产

二选一，执行前都要确认目标是生产项目。（仓库中没有记录生产环境目前用的是哪一种，确认后请删掉另一种，避免两种方式混用。）

```bash
# 方式 A：Supabase CLI（需要 link 到生产项目，并有数据库密码）
cd backend
npx supabase link --project-ref <生产 project ref>
npx supabase db push --dry-run     # 先查看将要执行哪些 migration
npx supabase db push
```

方式 B：在 Supabase 控制台的 SQL Editor 中，按文件名顺序粘贴执行新的 migration。这种方式不会写入 CLI 的迁移历史表，之后再用 CLI 时需要用 `supabase migration repair` 对齐。

### 6. 验证

- 在控制台确认新表、列、函数已经存在；
- 如果改了 RPC 签名，等 PostgREST 的 schema 缓存刷新（大约 1 分钟），或者执行 `notify pgrst, 'reload schema';`；
- 再部署依赖这次变更的后端，并检查日志中没有 `PGRST202` 或 `column ... does not exist`。

## 兼容性：先数据库还是先代码

| 变更类型 | 顺序 |
|---|---|
| 新增表、列（可为空或有默认值）、新函数 | 先数据库，再代码 |
| 修改 RPC 签名 | 先创建新签名（保留旧签名），部署代码后再删除旧签名 |
| 删除或重命名列、函数 | 先部署不再使用它们的代码，再执行删除 |
| 收紧约束或 RLS | 先确认线上代码和数据都满足新约束 |

## 常见错误

| 错误 | 原因 |
|---|---|
| `PGRST202`（找不到函数） | 代码先于 migration 部署，或者 schema 缓存还没刷新 |
| `column ... does not exist` / `schema cache` | 同上。创建面试接口会在 `hint` 字段中提示先执行 migration |
| `42501 user mismatch` | 以用户身份调用 RPC 时，传入的 `p_user_id` 与 `auth.uid()` 不一致 |
