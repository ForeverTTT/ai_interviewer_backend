# 用户反馈每日邮件提醒

> 状态：已实现；生产启用由 GitHub 开关控制 · 最后核对：2026-10-11
> 代码：[工作流](../../.github/workflows/feedback-digest.yml)、[发送脚本](../../backend/scripts/sendFeedbackDigest.js)、[汇总逻辑](../../backend/src/lib/feedbackDigest.js)

每天德国时间上午 9 点检查 `user_feedback`。有尚未通知的反馈才发送一封汇总邮件，没有新反馈则不发。汇总包含总数、帮助入口反馈数、面试体验反馈数、面试负面评价数和 Supabase 查看入口，不包含反馈原文或用户身份。

“新反馈”按 `digest_sent_at is null` 判断，涵盖此前未通知的记录，首次启用也会包含历史反馈。后台编辑旧反馈不触发再次通知。发送成功指邮件服务接受发送请求，不代表最终进入收件箱。

使用 GitHub Actions 独立运行，不依赖 Cloud Run 常驻实例。`Europe/Berlin` 时区随夏令时调整；GitHub 定时任务可能排队延迟，不能保证邮件整点到达。参见 [GitHub 时区语法](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#onschedule)和[定时任务限制](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)。

## 启用步骤

1. 按[数据库迁移发布流程](数据库迁移发布.md)审核并在生产数据库按顺序应用尚未执行的迁移：`20261010090000_user_feedback.sql`、`20261011090000_feedback_daily_digest.sql`。本地测试脚本不能用于生产。
2. 配置 Resend 发信服务。发件地址使用已验证的自有域名地址，参见 [Resend 域名配置](https://resend.com/docs/dashboard/domains/introduction)。创建有发送权限的 API Key，存入 GitHub Secrets。
3. 将工作流和后端代码合入仓库默认分支。在 GitHub **Settings → Environments → production** 配置下表项目，先保持发送开关关闭。
4. 在 Actions 中手动运行 **Daily user feedback email**，保持 `dry_run=true`。确认输出的待通知数量和数据库一致；此步骤不发邮件，也不改变通知状态。
5. 设置 `FEEDBACK_DIGEST_ENABLED=true`。先手动运行并设置 `dry_run=false`、`test_email=true`，向配置邮箱发一封测试邮件；这不会修改反馈通知状态，也不占用当天的汇总。确认收到后，定时任务会在每天上午 9 点检查。需要手动发送真实反馈汇总时，设置 `dry_run=false`、`test_email=false`；当天已成功发送过则跳过。

工作流代码本身不执行数据库迁移。新增配置只供独立邮件任务使用，无需修改 Cloud Run 环境变量或前端构建变量。

| production 配置 | 类型 | 值 / 作用 |
|---|---|---|
| `SUPABASE_URL` | Secret（已有） | 生产 Supabase URL |
| `SUPABASE_SERVICE_ROLE_KEY` | Secret（已有） | 仅服务端使用的生产服务密钥 |
| `RESEND_API_KEY` | Secret（新增） | Resend 发送 API Key |
| `FEEDBACK_DIGEST_TO` | Secret（新增） | 单个收件邮箱 |
| `FEEDBACK_DIGEST_FROM` | Variable（新增） | 例如 `FlowLab <feedback@已验证的自有域名>` |
| `FEEDBACK_DIGEST_DASHBOARD_URL` | Variable（可选） | HTTPS 查看入口；默认推导为当前 Supabase 项目的 Table Editor |
| `FEEDBACK_DIGEST_ENABLED` | Variable（新增） | 只有字符串 `true` 才启用真实发送，定时和手动发送均受此开关控制 |

## 本地验证

在 `backend` 目录运行，默认只预览，无需邮件密钥或收件地址：

```powershell
node scripts/sendFeedbackDigest.js --dry-run
node --test test/feedbackDigest.test.js
```

本地 Supabase 的数据库权限和快照测试（所有测试数据在事务结束后回滚）：

```powershell
# 从仓库根目录执行，仅连接本地容器。
Get-Content -Raw -Encoding utf8 backend/test/sql/feedback_digest.sql | docker exec -i supabase_db_ai_interviewer_backend psql -U postgres -d postgres -v ON_ERROR_STOP=1
Get-Content -Raw -Encoding utf8 backend/test/sql/user_feedback.sql | docker exec -i supabase_db_ai_interviewer_backend psql -U postgres -d postgres -v ON_ERROR_STOP=1
```

需要本地真实发信时，将 `backend/.env.example` 中的邮件变量填写到未跟踪的 `.env`，然后明确运行 `node scripts/sendFeedbackDigest.js --send`。本地 Supabase URL 无法推导云端查看入口，须显式填写 `FEEDBACK_DIGEST_DASHBOARD_URL`。不要把密钥写入代码、文档或前端变量。

## 失败、重试与去重

任务先保存固定反馈快照和收发件配置，记录首次发送尝试时间，再调用 Resend。发送被接受后，在数据库同一事务中记录邮件 ID，并只标记该快照中的反馈。过程中新增的反馈保持未通知状态，留待下一次汇总。

同一批邮件使用固定 `Idempotency-Key: feedback-digest/<batch-id>`，每次重试的邮件正文和收件配置完全相同。工作流失败后自动尝试三次，间隔 20 秒。数据库确认失败时，重新运行也会复用同一批次；不会提前把失败的反馈标为已发送。Resend 去重键保留 24 小时，参见[官方说明](https://resend.com/docs/dashboard/emails/idempotency-keys)。

为了防止“邮件已发出但数据库确认失败”在去重键过期后造成重复，首次尝试超过 **23 小时**的未确认批次会报错停止自动发送，需要人工核对。这种情况下不会丢弃待通知反馈，但后续邮件会等待该批次处理完成。修改收件人、发件人或查看入口时，若已有待处理批次，脚本也会停止并提示先处理旧批次。

核对时先查看 Actions 失败日志，以及 Supabase 的待处理批次（以下只在管理员 SQL Editor 执行）：

```sql
select id, digest_day, total_count, first_send_attempt_at, sent_at, provider_email_id
from public.feedback_digest_runs
where sent_at is null;
```

在 Resend 中核对对应去重键 / 请求记录：

- 确认邮件已经被接受：取真实 Resend 邮件 ID，调用 `select public.complete_feedback_digest('<batch-id>'::uuid, '<真实邮件 ID>');`，随后可恢复运行。
- 确认没有发出：才可执行 `update public.feedback_digest_runs set first_send_attempt_at = null where id = '<batch-id>'::uuid and sent_at is null;`，再重新运行。
- 无法确认：保留批次，继续核对；不要盲目清空状态或创建新批次。

停用时将 `FEEDBACK_DIGEST_ENABLED` 设为 `false`，不会删除反馈和批次记录。
