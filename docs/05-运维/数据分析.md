# 数据分析

> 状态：待配置（GCP 资源尚未创建，见 §1） · 最后核对：2026-10-04 · 技术文档：[埋点与数据分析](../03-技术与架构/通用机制/埋点与数据分析.md)

埋点日志的导出、查询、看板和数据删除。事件的含义和字段见技术文档。

## 1. 一次性配置

所有资源放在与 Cloud Run 相同的 GCP 项目中。

| 步骤 | 位置 | 做法 | 状态 |
|---|---|---|---|
| 1 | Cloud Logging → 日志存储 | （可选，立即可用）把 `_Default` 日志桶升级为 Log Analytics，可以用 SQL 直接查最近 30 天的日志，包括已有的 `auth_succeeded` | 未做 |
| 2 | BigQuery | 新建数据集 `analytics`，区域 `europe-west1`，默认分区过期时间 395 天 | 未做 |
| 3 | Cloud Logging → 日志路由器 | 新建 Sink：过滤条件 `resource.type="cloud_run_revision" AND jsonPayload.event=~"^analytics\."`；目标为 BigQuery 数据集 `analytics`；勾选"使用分区表" | 未做 |
| 4 | BigQuery → 数据集 `analytics` → 共享 | 把第 3 步 Sink 的写入服务账号设为该数据集的 `BigQuery Data Editor` | 未做 |
| 5 | BigQuery | 部署后走一遍完整流程（首页 → 登录 → 面试 → 报告），几分钟后会自动出现表 `run_googleapis_com_stdout`。确认 `jsonPayload` 下的字段后，创建 §2 的视图 | 未做 |
| 6 | Looker Studio | 按 §4 搭看板 | 未做 |

不要导出 Cloud Run 的原始请求日志：它包含 IP 和 User-Agent，只留在 Cloud Logging 里按 30 天过期。

费用：Cloud Logging 每月前 50 GiB 写入免费；BigQuery 每月前 10 GB 存储、1 TB 查询免费。当前规模预计为零。

## 2. 标准视图

所有查询都基于这些视图，不直接查 Sink 生成的表。

### 2.1 `analytics.events`

```sql
CREATE OR REPLACE VIEW `analytics.events` AS
SELECT
  timestamp AS loggedAt,                                          -- 分区列，查询时用它限定时间
  COALESCE(SAFE_CAST(jsonPayload.occurredAt AS TIMESTAMP), timestamp) AS occurredAt,
  jsonPayload.event AS event,
  SAFE_CAST(jsonPayload.schemaVersion AS INT64) AS schemaVersion,
  jsonPayload.source AS source,
  jsonPayload.userId AS userId,
  jsonPayload.anonymousId AS anonymousId,
  jsonPayload.sessionId AS sessionId,
  jsonPayload.interviewId AS interviewId,
  jsonPayload.pagePath AS pagePath,
  jsonPayload.referrerHost AS referrerHost,
  jsonPayload.utmSource AS utmSource,
  jsonPayload.utmMedium AS utmMedium,
  jsonPayload.utmCampaign AS utmCampaign,
  jsonPayload.uiLocale AS uiLocale,
  jsonPayload.appVersion AS appVersion,
  jsonPayload.deviceType AS deviceType,
  jsonPayload.browser AS browser,
  jsonPayload.os AS os,
  jsonPayload.props AS props
FROM `analytics.run_googleapis_com_stdout`
WHERE STARTS_WITH(jsonPayload.event, 'analytics.')
  -- 排除 PR 预览和本地构建的前端事件；服务端事件的 appVersion 为 NULL
  AND (jsonPayload.appVersion IS NULL
       OR (jsonPayload.appVersion != 'dev' AND NOT STARTS_WITH(jsonPayload.appVersion, 'preview-')));
```

注意：

- Sink 只为出现过非空值的字段建列。某个字段（例如 `utmMedium`）还没有出现过时，视图会报错，先把它写成 `CAST(NULL AS STRING) AS utmMedium`，等出现后再改回来。
- `occurredAt` 是事件发生时间，适合做分析；`loggedAt` 是分区列，**查询时一定要用 `loggedAt` 限定时间范围**，BigQuery 才只扫描对应分区。
- 下文查询中 `event` 的值带前缀，例如 `'analytics.interview_started'`。

### 2.2 `analytics.feature_usage`

把事件映射到功能，用于判断哪个功能更常用、更受欢迎。"用了一次"优先用有明确意图的动作，纯浏览型功能用有效停留 30 秒以上的页面。

```sql
CREATE OR REPLACE VIEW `analytics.feature_usage` AS
SELECT loggedAt, occurredAt, userId, feature
FROM (
  SELECT
    loggedAt, occurredAt, userId,
    CASE
      WHEN event = 'analytics.interview_started'
           AND JSON_VALUE(props, '$.source') = 'collection'              THEN 'question_bank'
      WHEN event = 'analytics.interview_started'                         THEN 'mock_interview'
      WHEN event IN ('analytics.resume_tailored',
                     'analytics.cover_letter_generated')                 THEN 'resume_tailor'
      WHEN event IN ('analytics.resume_parsed',
                     'analytics.resume_diagnosed')                       THEN 'resume_diagnose'
      WHEN event = 'analytics.gallup_completed'                          THEN 'gallup'
      WHEN event IN ('analytics.offer_plan_saved',
                     'analytics.growth_task_completed')                  THEN 'growth_center'
      WHEN event = 'analytics.experience_shared'                         THEN 'experiences'
      WHEN event = 'analytics.page_left'
           AND SAFE_CAST(JSON_VALUE(props, '$.activeSec') AS INT64) >= 30 THEN
        CASE pagePath
          WHEN '/interview/:id/report' THEN 'report'
          WHEN '/dashboard'            THEN 'growth_center'
          WHEN '/notes'                THEN 'question_bank'
          WHEN '/experiences'          THEN 'experiences'
        END
    END AS feature
  FROM `analytics.events`
  WHERE userId IS NOT NULL
)
WHERE feature IS NOT NULL;
```

### 2.3 `analytics.feedback_latest`

每次反馈只保留最终结果（同一个 feedbackId 取最后一条）。

```sql
CREATE OR REPLACE VIEW `analytics.feedback_latest` AS
SELECT
  loggedAt,
  occurredAt,
  userId,
  interviewId,
  JSON_VALUE(props, '$.feature') AS feature,
  JSON_VALUE(props, '$.rating') AS rating,
  JSON_VALUE(props, '$.reasons') AS reasons
FROM `analytics.events`
WHERE event = 'analytics.feedback_submitted'
QUALIFY ROW_NUMBER() OVER (PARTITION BY JSON_VALUE(props, '$.feedbackId') ORDER BY occurredAt DESC) = 1;
```

## 3. 指标与查询

### 3.1 核心指标

| 指标 | 定义 | 用途 |
|---|---|---|
| 日活 / 周活 / 月活 | 当期有任一事件的不重复 `userId` | 整体规模 |
| 新用户数 | `login_completed` 且 isNewUser = true；以 Supabase `auth.users` 核对 | 增长 |
| 激活率 | 新用户中，注册后 24 小时内产生 `interview_completed` 的比例 | 新用户是否体验到核心价值 |
| 主漏斗 | 首页 `page_viewed` → `login_started` → `login_completed` → `setup_submitted` → `interview_started` → `interview_completed` → 报告页 `page_viewed` | 找出流失最大的环节 |
| 留存 | 按首次活跃周分组，第 1 / 7 / 30 天仍有 `interview_started` 的比例 | 产品粘性 |
| 面试完成率 | `interview_completed` ÷ `interview_started`，按 mode、面试官类型、难度、语言拆分 | 面试体验质量 |
| 中途离开 | `interview_abandoned` 的 messageCount、elapsedSec 分布 | 定位用户在面试的哪个阶段离开 |
| 功能渗透率 | 各功能周活跃用户 ÷ 总周活（§3.3） | 哪些功能有人用 |
| 功能回头率 | 第一次使用某功能后 14 天内再次使用的比例（§3.3） | 用户是否喜欢 |
| 好评率 | 各功能 👍 ÷ 全部反馈（§3.4） | 结果质量 |
| 报告阅读深度 | 报告页 `page_left` 的 activeSec 之和、maxScrollPct 中位数 | 报告是否有价值 |
| 再练率 | 看完报告后 7 天内产生新的 `interview_started` 的比例 | 闭环是否形成 |
| 能量值消耗 | 人均消耗、按功能拆分、用完赠送的 1000 所需天数、`tokens_insufficient` 频率 | 付费定价依据 |
| 渠道质量 | 按 utmSource 分组的注册数、激活率、留存 | 投放决策 |
| AI 质量 | `interview_completed` 的 latencyMs P50 / P95；失败率看排障日志中的 `finalize_failed` | 稳定性 |
| 前端健康 | `client_error`、`api_request_failed` 按页面和接口计数；`web_vitals` 的 LCP / INP P75 | 体验问题 |

### 3.2 常用查询

日活：

```sql
SELECT DATE(occurredAt, 'Europe/Berlin') AS day, COUNT(DISTINCT userId) AS dau
FROM `analytics.events`
WHERE loggedAt >= TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 30 DAY)
  AND userId IS NOT NULL
GROUP BY day
ORDER BY day;
```

面试完成率：

```sql
WITH started AS (
  SELECT interviewId,
         JSON_VALUE(props, '$.mode') AS mode,
         JSON_VALUE(props, '$.interviewerType') AS interviewerType
  FROM `analytics.events`
  WHERE event = 'analytics.interview_started'
    AND loggedAt >= TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 30 DAY)
),
completed AS (
  SELECT DISTINCT interviewId
  FROM `analytics.events`
  WHERE event = 'analytics.interview_completed'
    AND loggedAt >= TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 37 DAY)
)
SELECT mode, interviewerType,
       COUNT(*) AS started,
       COUNTIF(c.interviewId IS NOT NULL) AS completed,
       ROUND(COUNTIF(c.interviewId IS NOT NULL) / COUNT(*), 3) AS completionRate
FROM started s
LEFT JOIN completed c USING (interviewId)
GROUP BY mode, interviewerType
ORDER BY started DESC;
```

能量值消耗结构：

```sql
SELECT JSON_VALUE(props, '$.feature') AS feature,
       COUNT(*) AS times,
       SUM(SAFE_CAST(JSON_VALUE(props, '$.amount') AS INT64)) AS tokens
FROM `analytics.events`
WHERE event = 'analytics.tokens_spent'
  AND loggedAt >= TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 30 DAY)
GROUP BY feature
ORDER BY tokens DESC;
```

### 3.3 功能常用度与受欢迎程度

渗透率和人均频次（最近 30 天）：

```sql
WITH active AS (
  SELECT COUNT(DISTINCT userId) AS n
  FROM `analytics.events`
  WHERE loggedAt >= TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 30 DAY)
    AND userId IS NOT NULL
)
SELECT
  feature,
  COUNT(DISTINCT userId) AS users,
  ROUND(COUNT(DISTINCT userId) / ANY_VALUE(active.n), 3) AS reach,
  ROUND(COUNT(*) / COUNT(DISTINCT userId), 2) AS usesPerUser
FROM `analytics.feature_usage`, active
WHERE loggedAt >= TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 30 DAY)
GROUP BY feature
ORDER BY reach DESC;
```

14 天回头率（只统计首次使用已满 14 天的用户；间隔 1 小时以内的视为同一次使用）：

```sql
WITH firsts AS (
  SELECT userId, feature, MIN(occurredAt) AS firstAt
  FROM `analytics.feature_usage`
  GROUP BY userId, feature
  HAVING MIN(occurredAt) <= TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 14 DAY)
)
SELECT
  f.feature,
  COUNT(DISTINCT f.userId) AS triedUsers,
  ROUND(COUNT(DISTINCT u.userId) / COUNT(DISTINCT f.userId), 3) AS repeat14d
FROM firsts f
LEFT JOIN `analytics.feature_usage` u
  ON u.userId = f.userId
 AND u.feature = f.feature
 AND u.occurredAt > TIMESTAMP_ADD(f.firstAt, INTERVAL 1 HOUR)
 AND u.occurredAt <= TIMESTAMP_ADD(f.firstAt, INTERVAL 14 DAY)
GROUP BY f.feature
ORDER BY repeat14d DESC;
```

把渗透率、人均频次、回头率、好评率放在一张表里看：

| 情况 | 判断 |
|---|---|
| 渗透率高，回头率高 | 核心功能，重点投入 |
| 渗透率低，回头率高 | 用过的人喜欢但知道的人少，优化入口和引导 |
| 渗透率高，回头率低 | 大家试过但不想再用，查体验问题 |
| 渗透率低，回头率低 | 考虑简化或下线 |

注意：优势测试本来就是一次性功能，回头率天然低，要看完成率和好评率；各功能价格不同（面试 300，简历解析 50），比较时考虑价格；每个功能至少有几十个用户试过，结论才有意义。

### 3.4 反馈

各功能好评率：

```sql
SELECT feature, COUNT(*) AS responses, ROUND(COUNTIF(rating = 'up') / COUNT(*), 3) AS helpfulRate
FROM `analytics.feedback_latest`
WHERE loggedAt >= TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 30 DAY)
GROUP BY feature
ORDER BY responses DESC;
```

差评原因分布：

```sql
SELECT feature, reason, COUNT(*) AS times
FROM `analytics.feedback_latest`, UNNEST(SPLIT(reasons, ',')) AS reason
WHERE rating = 'down'
  AND loggedAt >= TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 30 DAY)
GROUP BY feature, reason
ORDER BY feature, times DESC;
```

反馈率（反馈数 ÷ 看到结果的次数）太低时，好评率不可靠，说明入口不够显眼。

## 4. 看板（Looker Studio）

1. **总览**：日活 / 周活趋势、新用户、激活率、本周面试完成数。
2. **漏斗**：主漏斗各步转化率，可按渠道、界面语言、设备筛选。
3. **面试质量**：完成率拆分、中途离开分布、报告生成耗时、报告好评率。
4. **功能**：各功能渗透率、回头率、好评率。
5. **能量值**：消耗结构、余额不足次数、用完赠送额度的时间分布。
6. **留存**：按周的留存矩阵。
7. **前端健康**：报错、接口失败、页面性能。

看板数据量大以后，用 BigQuery 定时查询每天把明细聚合到 `analytics.daily_metrics`，看板读汇总表。

## 6. 删除用户数据

用户要求删除数据时（GDPR 删除权），除了 Supabase 中的业务数据，还要删除 BigQuery 中的埋点：

```sql
-- 1. 找出该用户用过的匿名 ID（登录前的行为）
CREATE TEMP TABLE ids AS
SELECT DISTINCT jsonPayload.anonymousId AS anonymousId
FROM `analytics.run_googleapis_com_stdout`
WHERE jsonPayload.userId = @userId AND jsonPayload.anonymousId IS NOT NULL;

-- 2. 删除按 userId 或这些匿名 ID 记录的事件
DELETE FROM `analytics.run_googleapis_com_stdout`
WHERE jsonPayload.userId = @userId
   OR jsonPayload.anonymousId IN (SELECT anonymousId FROM ids);
```

- 两条语句在 BigQuery Studio 里作为同一个脚本运行，把两处 `@userId` 换成带引号的用户 UUID（例如 `'7f3a…'`）。
- 最近约 90 分钟内写入的行还在流式缓冲区中，`DELETE` 会报错，过一段时间再执行。
- Cloud Logging 中的原始日志不能按条删除，30 天后自动过期。
- 处理完在内部记录：处理日期、用户 ID、操作人。

目前没有账号注销流程，以上作为手动操作；以后有注销流程时，在流程中自动执行。

## 7. 排查

| 现象 | 检查 |
|---|---|
| BigQuery 没有数据 | Cloud Logging 中按 `jsonPayload.event=~"^analytics\."` 能否看到日志；Sink 的写入服务账号是否有数据集权限；Sink 是否报错（日志路由器页面） |
| 没有客户端事件 | 浏览器是否已同意 Cookie；Network 面板中 `/api/ux-events` 是否返回 204；后端日志是否有 `ux_events_rejected` |
| 某个事件缺失 | 后端日志中搜 `analytics_event_rejected`，看 `analyticsEvent` 和 `reason`（unknown_event / invalid_props / props_too_large） |
| Sink 写入报错 | 多半是某个顶层字段类型变了；顶层字段必须保持固定类型，变化的数据放进 props |
